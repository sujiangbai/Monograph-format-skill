## 3. automatic intent 与可执行能力分离

### 3.1 两种不可混用的验证上下文

P3 冻结两种显式验证上下文。调用者必须选择其一，缺失、未知或混用时失败关闭。

| 上下文 | 目的 | automatic 属性的 capability 要求 | 允许产物 | 禁止事项 |
| --- | --- | --- | --- | --- |
| declaration/intent validation | 验证冻结的目标格式意图、属性类型、单位、作用域、层级、来源和未来能力绑定 | availability 只使用 unavailable、reserved、implemented；未实现的 executor/auditor 保持 reserved，稳定 capability ID 必须存在且声明未来所有者 | 治理已批准的规则资产，以及 disabled、runtime-ineligible、non-delivery 的组合报告和实现退出证据 | 不得执行、不得签发运行资格、不得导入现行入口 |
| strict execution validation | 判断某属性是否可在具体运行中自动执行 | executor=implemented、auditor=implemented，并满足运行时 snapshot 和后续门禁 | 仅在后续 P4-P7/P6 已获批准的执行路径中使用 | 不得把 unavailable、reserved、stub 当作 implemented，不得自动降级后继续执行 |

规则中的 `automatic` 表示经冻结的目标格式意图和预期执行模式，不代表当前仓库已经能执行。P3 不得为了通过注册表校验而把它改为 report、blocked_qa 或 qa，也不得声明虚假的 implemented capability。

### 3.2 P3 intent 共存的唯一条件

reserved capability 与 automatic intent 仅在以下条件全部满足时可以共存：

1. 验证上下文显式为 declaration/intent；
2. 规则资产已通过治理批准，并以 asset `activation=approved`、rule `status=approved` 进入 composer；未批准、disabled 或其他状态不得被跳过后形成空合成“通过”；
3. 运行启用仍由版本化 feature manifest 中 `monograph_base_v041=false`、显式 intent entry gate、最终 Profile `activation=disabled` 共同关闭；
4. runtime eligibility、final_ready eligibility 和 delivery eligibility 均为 false；
5. 相关 execution evidence 固定 non_delivery=true；
6. capability ID、未来实现工作流、预期 executor/auditor 配对和测试 ID 均可追踪；
7. 现行 `run_monograph.py`、`SKILL.md`、适配器和默认执行入口不导入 intent adapter；
8. 没有 `--force`、skip-approval、skip-audit、公共 CLI 或其他旁路。

任何一项不满足都必须失败，不得静默降级为“可运行但只报告”。

治理批准和运行启用是两套状态：`activation=approved`/`status=approved` 只证明规则资产可进入声明/意图组合，不证明 DOCX 能力可执行。P3 的 compose pass 还必须满足非空覆盖守恒：预期 approved rule/property inventory 与实际 candidate/proposed-resolution inventory 可以逐项双向核对；候选数为零、预期组合键没有 proposal/blocking record、任一 approved rule 或 property binding 未被消费、或出现无来源候选时均失败。不得用“没有报错但输出为空”作为合成通过。

### 3.3 运行资格的必要条件

后续执行资格必须同时证明：

- registry 中目标 executor capability 为 implemented；
- registry 中对应 auditor capability 为 implemented；
- 本次运行的 capability-snapshot 对两者均记录 available=true；
- snapshot、规则资产、最终执行 Profile、输入和执行证据指纹一致；
- P6 状态机、结构审批、冲突审批、允许变化、审计和防旁路门禁通过；
- 对应 P4/P5 能力已通过独立实现 PR、测试和用户授权。

以上是合取条件，不能由单个 feature flag、静态 registry 声明、测试 fixture 或角色自我声明替代。blocked/report/qa stub、占位函数、只返回 pass 的 auditor、未绑定实现证据或仅存在名称的 capability 均不得标记为 implemented。

### 3.4 P4/P5 后的受控转换

P4/P5 只能通过独立获批 PR 改变 capability availability 和实现证据。能力转为 implemented 时：

- 不得暗改 P3 已冻结的规则值、mode、scope、层级或来源；
- 必须绑定实现版本、auditor、测试和 capability evidence；
- 必须对 intent 资产重新运行 strict execution validation；
- 如果执行实现证明原规则不可表达或不安全，必须建立新迁移和新方案授权，不能就地改写规则以适配代码。

## 4. P3 串行实施总则

原 V0.4.1 的 P3a/P3b 两个实现 PR 细化为四个强制工作流切片：

1. P3a-C：能力声明/执行校验合同与 composer 基准；
2. P3a-R：完整 production property registry 与能力映射；
3. P3b-B：基础对象第一批 monograph-base 规则与迁移；
4. P3b-O：其余通用对象、完整迁移、真实资产合成和最终追踪闭合。

后项只能从前项已合并且退出门禁通过后的最新 `main` 建立。每份实现任务书必须记录完整 40 位 entry SHA；若远端 main 已移动，立即停工，不得自行换基线。四项是最低拆分，不是最多 PR 数；任一项无法独立审查时必须继续拆小，禁止重新合成一个大 P3 PR。

所有部分实现进入 main 后仍默认关闭，不替换旧候选 Profile，不改变现行输出。CI 通过不等于允许 Ready、合并、启用或发布。

## 5. P3a-C：能力合同与合成基准

### 5.1 精确入口

- 方案前置：本附录经用户明确授权并合并；P1/P2 已合并证据保持通过。
- 分支前置：从包含本附录合并结果的远端 main 精确 SHA 创建，并在任务书和 Draft PR 中锁定该 SHA；不限定合并方法。
- 若需要修改旧 Schema、现行运行入口或本附录未允许的 P2 语义，停止并建立独立契约修订。

### 5.2 允许范围

未来实现 PR 可在单独确认的白名单内：

- 扩展现有 Profile V2 registry validator 的显式 declaration/intent 与 strict execution 上下文；
- 按第 3.5 节完整建立已冻结的新版本 Schema、generated resources、matrix 1.1 route 和完全合成 fixture，不修改旧版本；
- 在 `profile_v2_composer.py` 提供公开、显式命名且默认不可达的内部构件接口 `compose_intent_profile_v041(...)`，只消费治理已批准的 2.2 规则资产并生成禁用的 intent 产物；P3b 不得依赖 tests 中的 private `_ContractAdapter`；
- 新增或修改相邻的纯 JSON 内部校验/benchmark 构件；
- 新增 capability truthfulness、上下文隔离、composer benchmark、确定性和隐私测试；
- 建立完全合成的规则资产规模预测清单和内部 benchmark 配置。

未来文件路径只能在 P3a-C 任务书中作为“拟新增/拟修改”白名单确认，不得被本方案描述成已经存在。

### 5.3 禁止范围

- 不创建完整 production 属性、monograph-base 规则或旧 Profile 迁移资产；
- 不修改 DOCX、Word、`run_monograph.py`、`SKILL.md`、适配器、公共 CLI 或发布文件；

### 5.4 退出门禁与测试族

- declaration/intent 与 strict execution 两个上下文均为显式、封闭、失败关闭；
- strict execution 的既有拒绝行为不放宽；
- intent 产物不能进入现行执行路径，不能通过改 flag、复制、重盖指纹取得运行资格；
- unavailable、reserved、implemented、stub/unknown 的正反测试齐全；`planned` 只允许出现在 trace/workflow projection，不是 registry availability；
- capability ID、executor/auditor、feature、snapshot 和证据引用不存在孤立或虚假映射；
- 新版本工件执行 cross-artifact rejection；registry/schema/catalog/generated resource 双向差集为零；fingerprint inventory 精确覆盖新版本且旧 inventory/指纹不漂移；
- 旧 2.0/2.1/2.2 工件不能自动升级、不能以 read-compatible 冒充 P3 intent，新旧 route 组合未知时失败关闭；
- `monograph_base_v041` 缺失或 false 时 intent 入口拒绝；测试显式 true 还必须满足既有 schema/composer 依赖，但结果仍只能是 disabled、runtime-ineligible、non-delivery；
- 旧 `compose_profile`、2.1 registry、P2b report/final 2.2 的 canonical bytes、语义指纹和拒绝行为回归不变；
- approved 资产非空覆盖守恒通过：预期 rule/property inventory、实际 candidates、proposals/blockers 双向可核对，零候选或未消费 approved rule 明确失败；
- synthetic composer benchmark 冻结机器、Python、OS、运行命令、输入规模、headroom、支持上限和 stop/go 阈值；

## 12. 内部 JSON 合成性能门禁

### 12.1 两阶段基准

- P3a-C：用完全合成资产建立基线、支持上限和 stop/go 阈值；
- P3b-O：用仓库内真实完整 monograph-base 资产复测相同指标和方法。

P3a-C 的代表规模必须来自 P3b 规划清单的预计规则/属性计数，并记录明确 `headroom_factor > 1`；不得按页数、书稿字数或随意整数设定。预计计数、headroom、代表规模和支持上限在 P3a-C benchmark 配置中冻结后，P3b 不得为通过测试而下调。

### 12.2 输入维度

每个 benchmark 至少记录：

- rule asset 数；
- property binding/candidate 总数；
- semantic object+property key 数；
- 同键候选最大值和分布；
- scope 重叠密度；
- subset、crossing、disjoint 比例；
- 同层冲突数；
- approval-required 数；
- 递归/分区最大深度和总分区数。

### 12.3 输出与资源指标

至少记录：

- wall time；
- peak memory/RSS，使用该平台可复现且在配置中声明的方法；
- 输入和输出 JSON 字节数；
- partition、candidate group、conflict、proposal 数；
- expected approved rule/property inventory、已消费 rule/property、candidate、resolution/blocking record 数及双向差集；
- composition report 和 final profile 的确定性 semantic fingerprint；
- 重复运行和输入排列随机化后的字节/指纹一致性。

所有结果绑定完整 commit SHA、Python 版本、OS/build、CPU、内存、运行命令、重复次数、预热策略和测试数据生成参数。不同环境的数字不得直接混算。

### 12.4 三层测试预算

| 层级 | 目的 | 执行位置 | 要求 |
| --- | --- | --- | --- |
| 快速确定性回归 | 检查小规模语义、排列、指纹和失败关闭 | 全部常规 CI matrix | 不减少任何功能测试，避免长耗时基准重复占用全部平台 |
| 代表性基准 | 验证预计完整资产+headroom | 冻结的参考机器/运行方法 | 有明确 wall time、RSS、输出大小和 stop/go 阈值 |
| 最终完整回归 | P3b-O 的真实完整 base 资产复测 | 冻结环境并保留结构化结果 | 指标与 P3a-C 同构，必须满足支持上限和确定性门禁 |

该门禁只适用于内部纯 JSON registry/composer，不得外推为 DOCX、上千页、Word、渲染或 V0.4.4 性能。

### 12.5 stop 条件

任一情况发生即阻塞 P3b 或其闭合：

- scope 递归、分区守恒或稳定 ID 失败；
- 相同语义输入产生不同 canonical bytes 或 fingerprint；
- 峰值内存异常、进程失败或超过冻结预算；
- 实际 P3b 资产超出冻结支持上限；
- 代表性或完整基准不能在批准测试预算内完成；
- 为通过基准需要抽样省略规则、候选、冲突或作用域。
- approved 资产产生零候选、任一 approved rule/property binding 未消费、预期组合键无 resolution/blocking record，或实际候选无可追溯来源。

发生 stop 时必须建立独立 P2/性能契约修订，不能以抽样成功、单平台成功、平均值掩盖峰值或“后续优化”宣称通过。

## 16. 残余风险与停工条件

- declaration/intent validator 增加新的验证语境，若 API 命名或默认值不够封闭，弱模型可能误用；因此缺省必须 strict 或拒绝，intent 必须显式且不可被运行入口导入。
- 第 3.5 节的新版本链解决当前已知合法实例变化；完整注册表若再暴露该链仍不能表达的新约束，必须先建立后续显式契约修订，不能在 P3a-R 临时加 Python 私有规则或原地扩大 2.2/2.3。
- P3b 预计规则数在真实资产建立前仍是预测值；P3a-C 必须记录预测来源和 headroom，P3b-O 必须用实际计数复测。
- 六份旧候选 Profile 存在同名规则和值漂移；语义指纹+rule ID 能防误匹配，但拆分/移层仍需逐项迁移证据。
- monograph-base 与领域 Profile 的保护边界可能相邻；无法证明是通用格式时必须标记 future-primary/protected-boundary 或 blocked_qa。
- P2b-C 成对分区在候选密度上升时可能出现非线性成本；超限必须停工修订 P2，不能把性能风险推给 P4/P5 executor。
- 本附录不提供恶意宿主防护、数字签名或来源认证；既有 SHA-256 仍只用于一致性和陈旧/非预期变化检测。
