# format-monograph V0.3.0：整书可靠性与跨 Agent 可移植运行

## 总结

将尚未合并的 V0.2.7“跨 Agent 可移植性与运行清单”吸收进 V0.3.0，不再单独建立 V0.2.7 方案文件。保留 V0.2.6 已有的开放 `SKILL.md`、规则优先级、内容保护和审计机制，重点解决整书运行缓慢、结构识别不一致、目录编号错误、图表漏处理、附录遗漏和中断重跑问题。

参考其他 skill 的标准入口、渐进式资料加载、运行前检查和质量门禁思想，但不复制其代码或平台专用提示。V0.3.0 同时成为整书可靠性升级和跨 Agent 运行标准化方案。

## 接口与可移植性

- 新增跨平台统一编排脚本，封装现有盘点、应用、审计、字段更新和渲染脚本：
  - `run_monograph.py prepare <input.docx> --profile <profile.json> --work-dir <directory>`
  - `run_monograph.py apply --work-dir <directory> --structure-map <approved.json>`
  - `run_monograph.py finalize --work-dir <directory>`
  - `run_monograph.py verify --work-dir <directory>`
  - `run_monograph.py status --work-dir <directory> --json`
  - 所有阶段支持 `--resume`，不得覆盖原稿。
- 新增本地 `run-state.json`，记录源文件、配置和结构映射指纹、能力快照、阶段状态、缓存、阻塞 QA、产物及耗时。书稿文字不得写入状态文件或公开日志。
- 统一状态为 `analysis_only`、`prepared`、`blocked_qa`、`candidate_ready`、`final_ready` 和 `failed`；不同 Agent 不得自行解释或提高交付等级。
- `check_environment.py --json` 输出标准能力清单，分别报告 Python、DOCX、字体、渲染、目标 Word、字段更新和多模态资料读取能力。
- 新增“跨 Agent 运行清单”参考文件；Codex、Claude Code、Gemini CLI、Copilot 和其他 Agent 均执行相同的准备、QA、应用、审计和交付检查。
- 保持 `SKILL.md` 简洁，将整书运行细节、状态说明和故障恢复放入引用文件，平台适配层只处理发现位置和调用方式。
- 结构映射升级并兼容现有 1.4，将 `heading_1` 等旧角色映射到统一的章题、二至四级标题和附录角色，避免 profile 规则检测成功但实际零命中。

## 整书处理

- 首次盘点后缓存 OOXML 索引、对象哈希、结构角色、字体、字段、图表及分节信息；输入或规则未变化时只重跑受影响阶段。
- 对同类问题集中提出一次 QA；例外单独列出。某章节存在未决问题时只冻结相关章节或对象，其他已确认范围继续处理。
- 标题层级、编号重启或目录范围不明确时，暂停相关编号与目录生成；不得把存在错误编号的稿件标记为正式完成。
- 目录仅收录批准的标题角色，不再依赖可能吸收无关段落的宽泛大纲范围。目录与正文页码分别从阿拉伯数字 1 开始。
- 识别附录但保留书稿已有附录编号；附录中的图、表和公式编号同样保持。缺失、重复或异常编号只报告并等待确认。
- 原目录已有附录时，新目录保留附录；原目录没有时不自动加入，只在报告中提示。
- 表格分类为数据表、三线表、网格表、图版表、提示框、版式表和未知表。不得默认首行为表头；支持多行表头整体重复及必要的横向分隔线。
- 表格默认居中、无环绕、无底纹，不改变文中锚点、顺序和相邻内容。一般主线 1.0 pt、内部线 0.5 pt、无左右外边框；具体边框拓扑根据表格结构确定。
- 仅删除能够证明无意义的单元格首尾空段；不删除内容段落。图表后同页有后续内容时插入一个真实空段，分页后位于页首则自动移除。
- 图片保持原锚点、顺序、环绕、裁剪和所在单元格。仅对超出版心或引起明显分页缺陷的图片自动缩小，不自动放大；等高图组、疑似图名和其他调整进入分组 QA。
- 试排稿只选择代表性片段：书名与目录、各级标题、附录以及每类图表原则上各 1–2 个实例，优先覆盖异常位置。
- 单个试排稿默认不超过约 30 个渲染页；覆盖不足时拆为多个连续片段，不生成整篇候选稿。试排稿不作为整书分页验收依据。

## 字段、审计与交付

- 在一次性临时副本中调用 Word 或批准的等效后端更新目录、页码和交叉引用。
- 只回写批准的字段结果；正文、公式、MathType/OLE、媒体、嵌入对象或未批准 OOXML 出现变化时拒绝临时副本。
- 字段更新前后执行内容指纹、OMML、OLE、媒体、字体和对象关系审计，不能用“Word 可以打开”代替完整性验证。
- 正式整书稿必须完成全部页面的目标软件渲染检查；渲染失败或存在关键 QA 时只能交付限定范围的候选稿。
- 交付报告列出缓存命中、各阶段耗时、冻结范围、未决 QA、字段状态、受保护对象结果和逐页检查状态。
- 只有全部关键 QA 关闭、字段安全更新、内容审计通过并完成逐页视觉检查后，状态才能为 `final_ready`。

## 测试与治理

- 使用合成 DOCX 测试数百标题、复杂目录、多个附录、分节、公式、数百表格和大量图片；正式书稿及其内容不得进入仓库、日志或 CI 工件。
- 验证缓存命中、断点续跑、局部失效和输入变更后的正确重新盘点。
- 验证旧结构角色兼容、标题规则真实命中、目录只含批准对象及附录保留策略。
- 覆盖多行表头、复杂合并、图版表、无意义空段、浮动或裁剪图片，以及图表位置不变。
- 模拟 Word 改写 OLE 或媒体对象，确认字段结果被拒绝；安全结果必须能受控回写。
- 在四个首批 Agent 中使用相同提示、运行清单和合成输入执行独立上下文测试；没有实机条件的平台继续标记“待验证”。
- 从最新 `main` 创建 `plan/v0.3.0-whole-book-reliability`，新增不可覆盖的 V0.3.0 方案并更新索引。
- 方案 PR 获得明确批准并合并后，再建立 `skill/whole-book-reliability-v0.3.0` 实现分支。
- 实现通过合成测试、跨 Agent 检查和本地私密整书试运行后，再决定是否发布 `v0.3.0-rc.1`。

## 已确定默认

- 当前调用 skill 的用户明确格式要求始终是该任务的最高格式依据，但不能突破内容、原稿、公式和审计安全边界。
- V0.2.7 只作为设计来源并入 V0.3.0，不建立缺失的历史版本文件，也不修改 V0.2.6 方案正文。
- 外部 skill 只借鉴通用方法，不引入其平台绑定、目录结构或规则文本。
- 运行产物、缓存、QA 和书稿始终保存在用户指定的本地任务目录，不提交公开仓库。
