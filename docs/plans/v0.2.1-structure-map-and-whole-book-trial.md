# format-monograph V0.2.1：结构映射与整书试排加固

## 背景

真实教材 DOCX 可能同时包含静态目录、手工编号标题、直接格式标题、真实标题样式、跨页表格、异形分节和空白尾页。仅按现有 Word 样式或编号正则直接修改，会把目录条目误当成正文标题，或把正文中的普通编号段落误当成标题。

V0.2.1 引入“盘点 -> 结构映射 QA -> 格式应用”的强制阶段。单章用于验证识别和排版规则，最终能力仍须接受整本 DOCX 并一次完成全书处理，不要求用户逐章操作或手工拼接。

本方案不保存或公开任何真实书稿、标题、图片、页码、路径、OCR 或渲染内容。所有仓库测试使用完全合成的文档。

## 已确认的试排决策

1. 标题按“章题 -> Heading 1、`x.x` -> Heading 2、`x.x.x` -> Heading 3、`x.x.x.x` -> Heading 4”映射。
2. 经确认的静态目录替换为真实 Word `TOC` 字段。
3. 经确认的图题和表题迁移为真实 `SEQ` 字段，保留原有“标题层级号 + 本节顺序号”编号语法；异常编号只报告。
4. 经结构和视觉检查确认无内容、无锚定对象且无版式用途的尾部空白页及无用分节应删除；用途不明时停止并 QA。
5. 简单行内变量、单位和短算式允许保留为文本；独立成行或复杂公式必须保持 OMML、MathType，或经验证由 LaTeX 转换为 OMML，禁止图片公式。
6. 本轮保留表格原有底色和边框，只应用获批的文字、表头和跨页规则。

## 新的结构映射阶段

### 1. 生成候选映射

`inspect_docx.py` 在常规 inventory 之外生成本地 `structure-map.json` 候选。映射至少包含：

- 文档内容指纹及每个候选段落的稳定文本哈希。
- 段落、表格、分节及对象的位置标识，不使用正文全文作为持久标识。
- 候选语义角色、编号模式、原样式、直接格式签名、置信度和冲突原因。
- 静态目录候选范围、正文起点候选和目录条目与正文标题的匹配结果。
- 图题、表题、公式题及编号语法候选。
- 尾部空白页/分节候选及“无正文、无表格、无绘图、无书签目标、无注释引用、无独立页眉页脚”的证据。
- 表格表头、跨页、超高行和续表候选。

候选映射保存在用户本地，不提交仓库。

### 2. QA 批准

Agent 汇报候选数量、冲突和风险。用户批准后，生成 `approved` 状态的任务结构映射；批准项记录段落位置、文本哈希和目标角色，避免用户逐条复录标题。

若源 DOCX 在批准后发生变化，内容指纹或目标哈希不匹配时必须停止，不能将旧映射套到新稿。

### 3. 应用顺序

应用阶段固定按以下顺序执行：

1. 验证源文件指纹、结构映射状态和目标哈希。
2. 将已批准的静态目录范围规范化为真实 `TOC`，保留范围外的书名、章名和其他前置文字。
3. 将批准的正文标题映射为 Heading 1-4，再建立关联样式的多级编号。
4. 将批准的图表题编号迁移为 `SEQ`；仅替换编号派生部分，题注说明文字保持不变。
5. 应用正文、标题、题注、表格、注释及其他获批格式。
6. 对确认的表头设置重复，对普通行设置禁止跨页拆分；超高行继续允许拆分并报告。
7. 删除已批准且再次验证为空的尾部空白页和无用分节。
8. 更新字段、执行内容和受保护对象审计，再渲染逐页检查。

## 静态目录安全规则

- 静态目录迁移必须使用用户批准的明确范围和范围哈希。
- 目录范围与正文标题无法可靠匹配时，报告差异；真实 `TOC` 只根据已批准正文标题生成。
- 范围外文字不得因目录迁移被删除。
- `TOC` 层级、点引导线和页码右对齐由配置控制。

## 题注与交叉引用安全规则

- 先识别题注角色、编号令牌和说明文字，再替换编号令牌。
- 支持章号、节号与本节顺序号组成的既有编号语法，不强制改成单一 `图 1.1` 模式。
- 题注迁移后建立书签，后续交叉引用使用 `REF`/`PAGEREF`。
- 无法唯一解释的编号、断链引用或疑似错误只报告，不自动改号或猜测目标。

## 空白页与分节安全规则

仅当以下条件全部满足时，尾部空白页/分节才可自动删除：

- 用户已批准删除该候选。
- 候选范围没有正文、表格、图片、公式、文本框或嵌入对象。
- 没有书签目标、脚注/尾注引用、批注锚点或交叉引用目标。
- 没有需要保留的独立页眉页脚、页码重启、纸张方向或纸张尺寸用途。
- 删除后源内容指纹、媒体、OMML 和嵌入对象审计仍通过。

任何一项不能证明时停止并生成阻塞 QA。

## 环境能力修正

环境检测改为分别报告：

- `inspection`：Python、`python-docx`、`lxml`。
- `profile_validation`：`jsonschema`。
- `docx_editing`：盘点依赖与写入能力。
- `rendering`：LibreOffice 或外部等效渲染器，加 PDF 页面渲染能力。

缺少配置验证包不能被笼统描述为完全不能读取 DOCX。Microsoft Word 可作为本地可选视觉验证器，但不得成为核心 Skill 的运行依赖。

## 整书能力与大文档处理

- 输入始终允许是包含全部前置页、正文、附录、答案和索引的单一 DOCX。
- 结构映射按全书生成，保持跨章编号、目录、书签、题注和交叉引用的一致性。
- 大文档处理采用确定性检查点和分批渲染，但输出仍是一份完整格式稿、一份完整审阅稿和一份全书报告。
- 最终验收逐页覆盖整本书，不以单章试排或抽样代替。

## 测试与验收

1. 合成文档同时包含静态目录伪标题和正文真实标题，验证两者不会混淆。
2. 验证四级编号模式映射、源指纹变化阻塞和目标哈希变化阻塞。
3. 验证真实 `TOC` 替换只影响批准范围。
4. 验证多级题注语法迁移为 `SEQ`，题注说明文字不变，异常编号仅报告。
5. 验证跨页表只对确认表头设置重复，保留原表格底色和边框。
6. 验证空白尾节满足全部条件时删除；含对象、书签、注释或独立页眉页脚时阻塞。
7. 验证简单行内表达式不被误转，图片公式仍阻塞。
8. 验证环境能力维度在缺少 `jsonschema`、渲染器或 PDF 页面工具时分别准确降级。
9. 验证原稿从不覆盖，正文、表格文字、脚注、尾注、批注、媒体及可编辑公式内容保持一致。
10. 在合成整书和真实本地书稿上逐页检查；真实书稿和结果不得进入仓库或 CI。
