# format-monograph V0.4.1：Profile 基础设施与分组执行详细方案

## 1. 定位、基线与非目标

本方案以 `main@bcb4e9087d2a2a988dbd6cc240fba40662742f88` 为唯一基线，把 V0.4.0 已冻结的 Profile 分层、`monograph-base`、统一入口和 Word 收敛要求拆成可独立评审、默认关闭且可回滚的 V0.4.1 实施序列。本方案自身只定义后续实现，不创建 schema、Profile、规则资产、测试、Skill 或 CLI，不改变当前运行行为，也不发布版本。

严格非目标：

- 不实现 `science-engineering-monograph`、`textbook-pedagogy`、`equation-heavy`、`engineering-drawing` 或 `code-heavy`；
- 不提交私有科学符号规范原文、截图、路径、书稿内容、对象载荷或私有哈希；
- 不实现 V0.4.3 的完整字符/层级/包级台账、原子检查点、局部失效、`--resume` 和失败隔离；
- 不执行 V0.4.4 的 1000/2000 页正式基准，不预设目标机器的性能阈值；
- 不承诺稳定公共 CLI、安装器、一键入口或外部兼容周期；
- 不把旧 `technical-textbook-layout*` 改名为新基础 Profile，也不让新旧 Profile 同时自动生效；
- 不修改 V0.4.0 或此前任何历史方案。

## 2. 当前架构风险与处理结论

基线审阅覆盖现有 Profile 1.0/1.1 schema、`validate_profile.py`、`_common.py` 属性集合、`apply_profile.py`、`run_monograph.py`、字段最终化脚本、六份候选 Profile 及现有测试。确认以下风险必须先于规则扩充解决：

| 风险 | 当前表现 | V0.4.1 处理 |
| --- | --- | --- |
| 工件职责混合 | 单个 JSON 同时保存证据、规则、冲突、审批和运行策略 | 分离规则资产、最终执行 Profile、审批、执行证据、冲突、迁移、能力和特性工件 |
| 权威模型失真 | `source_precedence` 排的是证据类型，无法表达安全层、模块作用域和任务覆盖 | 合成器使用不可覆盖安全层及属性级层级链；证据类型不再充当层级 |
| schema/执行器分裂 | schema 对 `properties` 宽松接收，Python 集合另行判断是否支持 | 属性注册表成为 schema、validator、composer、executor 的单一强类型来源 |
| 顺序依赖 | 旧数组顺序可被误当作决议顺序 | 规范化、稳定排序和属性级冲突算法禁止 last-write-wins |
| 旧规则污染 | 旧教材 Profile 含固定边距、固定行距、强制分页、长引文缩小等废弃值 | 只通过显式迁移清单逐项导入；默认不读入合成候选链 |
| 弱模型旁路 | 单脚本可被直接拼接为“完成” | 统一内部入口签发阶段证据；构件直调不能取得正式状态 |
| Word 终态过早 | 一轮目录/字段更新可能改变分页 | 第 7 PR 实现有界收敛；连续两轮一致、最多三轮 |
| 部分能力误启用 | 分阶段合并可能改变现行候选行为 | 每个实现 PR 均由仓库级特性默认关闭；版本退出门禁和另行授权后才可启用 |

## 3. 权威、安全与作用域

### 3.1 不可混淆的决议顺序

1. 安全不变量独立于格式层并且不可覆盖；
2. 当前用户/任务明确覆盖及后续 QA 决定；
3. 用户指定出版社要求或 DOCX 模板；
4. 已批准且只在自身语义对象范围内生效的功能模块；
5. 用户选择的书籍类型 Profile；
6. `monograph-base`；
7. GB/T 等标准仅补缺。

模块越界候选在合成前即拒绝。同层、同一规范化作用域、同一属性出现不同规范化值时形成阻塞冲突；不得按文件名、加载顺序、数组顺序、时间戳或最后写入决定。安全不变量不进入普通候选链，而是在候选产生前、合成后和执行前分别校验。

### 3.2 内容保护边界

本 Skill 不执行一般内容编辑。文字、标点、事实、数据、公式语义、题注文字、答案和参考文献内容始终不可修改。允许变化只包括批准的标题编号前缀重建、Word 派生字段结果，以及批准的目录、页码、交叉引用等派生结构；每项均须进入允许变化清单和审计。无法证明安全时保持并报告，不能用用户格式优先级覆盖安全不变量。

## 4. 工件模型与生命周期

### 4.1 工件类型

| 工件 | 规范职责 | 生命周期与持久化 | 仓库边界 |
| --- | --- | --- | --- |
| `layered-rule-asset` | 单一层的规则、作用域、属性值、公开来源摘要、置信度和规则状态 | 版本化资产；正式公共规则可持久化 | 可提交，但不得含规范全文、书稿文字、本地路径或私有证据 |
| `final-execution-profile` | 将本任务所选资产按属性合成后的扁平唯一执行输入 | 任务运行时产生；绑定输入、特性和审批指纹；任务结束后按用户本地策略保留 | 不提交；只在本地任务目录保存，不含书稿文字 |
| `qa-approval-artifact` | 用户、结构和冲突决议，例外对象及允许变化清单 | 任务运行时产生；不可变追加；批准后绑定输入和最终 Profile 指纹 | 不提交；不得记录书稿正文，只记录稳定对象 ID、决定和非敏感指纹 |
| `legacy-migration-manifest` | 旧 1.0/1.1 Profile/规则到新规则的保留、修改、移层、拆分或废弃结果 | 版本化迁移资产；只有显式命令/内部入口选中时读取 | 可提交公开 ID 与摘要；不得复制私有证据或使旧规则自动启用 |
| `feature-activation-manifest` | 声明可用特性、依赖、默认值、实验状态和正式入口授权 | 仓库保存默认清单；运行时解析为任务快照 | 可提交默认全关清单；任务启用快照不提交 |
| `capability-snapshot` | Python、DOCX、字体、目标 Word、字段后端、渲染与多模态能力 | 每次 `prepare` 运行时产生并绑定运行 | 不提交；不得含令牌、账户、绝对私有路径 |
| `conflict-report` | 属性候选链、同层冲突、缺失、低置信度、越界和关闭证据 | 合成时产生；审批后作为审批工件引用 | 不提交；公开合成测试只用合成数据 |
| `execution-evidence-artifact` | 承载运行、测量、测试、Word 收敛和实现退出证据；与语义审批、环境快照和冲突报告分离 | 执行/验证时不可变追加；V0.4.1 只允许 diagnostic/implementation_exit | 不提交；公开测试只用合成结果，不含书稿文字、私有对象载荷或绝对路径 |

以上共 **8 类独立规范工件**。`conflict-report` 保持独立 `artifact_kind`，不内嵌为 `qa-approval-artifact`：它可在尚未有审批时生成，审批工件只通过稳定报告 ID 和语义指纹引用它。`execution-evidence-artifact` 也不得塞入 `capability-snapshot`、`qa-approval-artifact` 或万能 report。8 类工件均纳入 P1 schema、生命周期、交叉混装拒绝、指纹和隐私测试。

`execution-evidence-artifact` 至少包含 `evidence_id`、`evidence_class`、`non_delivery`、`evidence_scope`、producer 的稳定 `actor_id`/`actor_role`（不等于审批者）、tool/schema/capability versions、task/input/profile/structure/approval/ledger/Word environment bindings、measured results、技术 pass/fail、`created_at`、`supersedes` 引用、`final_ready_eligible`、不可变历史和规范化语义指纹。V0.4.1 producer role 只允许 `project_manager`、`developer` 或 `automated_qa`；这些 producer 权限不转化为语义审批权限。V0.4.1 schema 只接受 `diagnostic` 与 `implementation_exit`，遇到 `delivery` 必须在 schema 层拒绝。

每个工件顶层必须有 `artifact_kind`、独立 `schema_version`、稳定 ID、创建工具版本、输入指纹集合和规范化语义指纹。不同工件不能通过可选字段重新拼成旧式“万能 Profile”。时间、绝对路径、操作者显示名等非语义元数据不得进入语义指纹。

### 4.2 生命周期

`layered-rule-asset + feature defaults + task selections`
→ schema/registry 校验
→ 候选链与冲突报告
→ QA 审批工件
→ `final-execution-profile`
→ 结构审批绑定
→ 统一状态机执行
→ `execution-evidence-artifact` 不可变追加。

旧 Profile 只能走 `legacy reader → legacy-migration-manifest → 明确选择的新层资产候选`，不能直接进入执行 Profile。向后读取只表示能识别和报告 1.0/1.1，不表示认可、启用、自动迁移或兼容原行为。

### 4.3 运行时决策主体与权限

本节只约束 Skill 处理一份具体书稿时的格式、结构和 QA 决议，不授予 GitHub、操作系统、法律出版审批、版本发布或公共接口治理权限。`qa-approval-artifact` 的有效语义审批主体仅允许 `user` 和 `delegated_publisher`，并至少表达：

- `actor_id`：任务内稳定主体 ID，不保存不必要个人信息；
- `actor_role`：schema 枚举仅为 `user` 或 `delegated_publisher`；
- `decision_type`、`authority_scope`（对象、属性、章节、规则或冲突范围）；
- `authorization_reference`：`delegated_publisher` 必须引用用户在本任务内授予的稳定授权；`user` 引用当前任务主体绑定；
- `decision`、`reason`、`created_at`；
- 输入、最终 Profile、结构图和 `conflict-report` 的指纹；
- `previous_approval_id` 或等效不可变追加链。

`actor_role` 是声明，不自动产生权限。审批验证器必须同时校验主体角色、`decision_type`、`authority_scope` 和授权引用；任何越权、扩域、陈旧或指纹失配的审批工件均无效并进入 `blocked_qa`。`project_manager`、`developer` 或 `automated_qa` 尝试作为语义 approver 时必须被 schema/semantic validator 拒绝；记录该无效尝试不能成为让其进入合法审批枚举的理由。

| 运行时参与主体 | 使用的工件 | 可执行行为 | 明确禁止 |
| --- | --- | --- | --- |
| `user` | `qa-approval-artifact` | 确认用户格式覆盖、最终语义目录/标题层级、编号边界、受控结构变化、冲突选择、例外对象和保持原稿决定 | 覆盖安全不变量；修改作者内容；把真实技术失败改写为通过 |
| `delegated_publisher` | `qa-approval-artifact` | 仅在用户于本任务明确授予的出版社要求范围内决议，并引用该授权 | 自行扩大到未授权对象/属性/章节；取代用户作范围外终决 |
| `project_manager` | `conflict-report` 或 `execution-evidence-artifact` | 记录建议、独立审查和阻塞发现 | 签发 `qa-approval-artifact`；替用户创造格式要求或作书稿语义终决 |
| `developer` | `execution-evidence-artifact` | 作为 producer 提交实现测量、测试结果和技术 pass/fail | 签发 `qa-approval-artifact`；替用户决定格式或关闭语义冲突；改写失败事实 |
| `automated_qa` | `execution-evidence-artifact` | 作为 producer 记录测量、检测证据和客观 pass/fail | 签发 `qa-approval-artifact`；作用户语义决定；把检测失败改为通过 |

所有主体均不能覆盖安全不变量、授权内容编辑、绕过 `blocked_qa`、字段门禁或视觉门禁。用户可以批准“保持原稿”，使冲突对象以批准证据转为 `unchanged`，但不能把 `failed` 技术证据重写为 `pass`。规则明确、对象分类可靠、无冲突且注册模式为 `automatic` 时不要求逐段用户审批；只有结构、冲突、低置信度、例外和 QA 项进入审批链。

运行时审批工件不得被解释为 GitHub 合并、版本发布、能力启用或公共 CLI 授权；项目治理记录也不得反向冒充书稿运行时语义审批。

## 5. Schema、属性注册表与确定性合成

### 5.1 Schema 版本契约

- 新工件使用各自的 `2.0` schema；版本号按工件独立演进，不共享一个宽泛根对象。
- reader 必须显式分派 1.0、1.1 和 2.0；未知大版本拒绝，未知小版本仅在声明兼容且无未知强制字段时读取。
- 1.0/1.1 读入结果标记 `legacy_input=true`、`activation=disabled`，只可送入迁移器和报告器。
- 新 Profile 不接受 `source_precedence` 作为层级。证据类型保留在来源摘要中，层级由 `layer_kind` 和激活清单决定。
- schema 结构通过后仍必须通过属性注册、层级、作用域、安全、迁移和审批语义校验；任一阶段失败均不能生成正式执行 Profile。

### 5.2 强类型属性注册表

属性注册表是唯一真源。P1 必须先建立注册表自身的 schema、生成/机械核对接口、核心数据类型、单位与比较器接口，并提供足以驱动 8 类工件 schema 测试的最小测试属性；P2 和后续 PR 只能消费该接口，不得内置私有属性表、单位表或规范化表。P3 再填充完整 `monograph-base` 属性条目，而不是首次创建注册表机制。每个属性至少声明：

- 稳定 `property_id`、适用语义对象和允许层；
- JSON 类型、枚举/范围、规范单位、默认比较精度；
- 是否可覆盖、是否安全不变量、是否需要 QA；
- 规范化函数、冲突比较函数、执行器能力 ID 和审计器能力 ID；
- 缺失策略、未知对象策略、跨属性约束和测试 ID。

schema 由注册表生成或机械核对；validator、composer 和 executor 只能使用注册表导出的同一能力集合。注册但无执行器的属性只能是 `report`/`blocked_qa`，不能标为 `automatic`。执行器声明但注册表不存在的属性属于构建失败。

### 5.3 合成键与冲突

最小合成键为：

`semantic_object_kind + property_id + normalized_scope`

`normalized_scope` 至少包含文档/分节/语义角色/对象例外范围及互斥条件。整个 rule 对象不是胜负单位；同一 rule 的不同属性可以来自不同最终层。候选处理顺序：安全预检 → 作用域验证 → 属性规范化 → 层级排序 → 同层冲突检查 → 高层覆盖 → QA/缺失检查 → 安全后检。

每个最终属性保留：最终层和来源 ID、全部候选值、从低到高覆盖链、被排除候选及理由、模块作用域验证、置信度、冲突 ID、QA 决议 ID、安全检查结果、执行/保持/报告/阻塞模式。模块越界不进入候选链，但必须进入报告。

### 5.4 规范化与指纹

- 文本先做 Unicode NFC；不得改变规则值所表达的作者内容。
- 对象键、属性键和映射键按 Unicode 码点稳定排序；集合数组按稳定 ID 排序；语义有序数组保留声明顺序并额外验证唯一顺序键。
- 数值拒绝 NaN/Infinity 和二进制浮点歧义；注册表将数值规范为十进制定点字符串和规范单位，如 `pt`、`mm`、`percent`、`char`。
- 等价单位先按注册表换算并量化到规定精度，再比较和序列化；未经声明的单位转换拒绝。
- 规范 JSON 使用 UTF-8、LF、无 BOM、无无意义空白；语义指纹为 `sha256:` 加规范字节 SHA-256。
- 时间戳、绝对路径、运行 ID、显示顺序和非语义诊断不进入语义指纹；输入文件、规则资产、特性清单和审批工件指纹分别保留。
- 相同语义输入在不同平台、文件枚举顺序和 JSON 键顺序下必须得到相同规范字节和指纹。

### 5.5 批准与阻塞条件

正式规则资产必须 schema/registry/作用域/安全校验通过，规则状态为 approved，公开来源摘要不泄密，所有 automatic 属性具有执行与审计能力。冲突只有在有效的 `qa-approval-artifact` 记录候选、选择、权限范围、授权引用、`user` 或获授权 `delegated_publisher`、时间及输入/最终 Profile/结构图/冲突报告指纹后才关闭；项目经理建议或技术证据不能关闭语义冲突，仅有角色自我声明也不构成有效批准。

以下情况必须 `blocked_qa`：同层属性冲突；必要属性缺失；低置信度属性拟自动应用；对象无法分类且规则可能改变它；模块作用域不确定；迁移结果未确认；审批工件哈希失配；安全检查不通过。用户决定保持原状时以批准决定转为 `unchanged`，不能把冲突或失败降为“非关键”。

### 5.6 指纹信任边界

SHA-256 语义指纹和证据链用于证明工件之间的一致性、发现陈旧输入和检测非预期变化；它不是数字签名，也不提供来源认证或不可伪造性。V0.4.1 没有密钥、签名者、信任根、密钥存储或撤销模型，因此不能抵御能够控制宿主和状态目录的恶意调用者重写工件并重算整条指纹链。

V0.4.1 的防旁路目标只包括误调用、陈旧工件、普通越级和内部状态不一致。正式入口必须校验指纹绑定和证据关系，但不得把“指纹匹配”写成“已签名”或“可信来源”。若未来需要抵御恶意宿主，应另建数字签名与密钥治理方案；该能力不是 V0.4.1 完成条件。

## 6. 统一入口基础契约

V0.4.1 只实现可表达并可防旁路的基础状态机：

`prepare → awaiting_structure_approval → apply → ready_to_finalize → finalize → verify → final_ready`

- `prepare` 只检查能力、合成最终 Profile 并生成候选结构/冲突工件，不修改 DOCX。
- `apply` 只接受绑定输入和最终 Profile 指纹的批准工件；V0.4.1 可使用现有粒度的批准对象清单，但不能宣称 V0.4.3 全对象台账已完成。
- `ready_to_finalize` 要求本阶段批准目标闭合且无 `approved` 遗留；完整字符/包级覆盖证明留给 V0.4.3。
- `finalize` 只在一次性目标 Word 临时副本上按字段白名单工作；第 7 PR 实现最多三轮收敛。
- `verify` 严格只读，不修复、不格式化、不刷新字段。
- 状态 schema 可以表达 V0.4.0 定义的 `final_ready`，但 V0.4.1 的激活清单必须固定 `final_ready_eligible=false`。在 V0.4.3 完整字符/层级/包级台账、对象守恒和覆盖证明能力可用并通过以前，任何 `verify → final_ready` 转换都必须失败。
- 即使 `approved=0`、`blocked_qa=0`、`failed=0` 且 Word 已连续两轮收敛，缺少完整对象覆盖能力或证据时仍不得产生 `final_ready`。P1-P7 的测试产物和阶段报告统一标记 `non_delivery=true`、`evidence_scope=v0.4.1`，最多证明“V0.4.1 实现退出门禁通过”。

内部 `run_monograph.py` 或等效调度器是 Skill、弱模型和适配器取得受控阶段证据的唯一入口。构件脚本可用于测试，但不能签发正式状态。正式入口不得提供 `--force`、`skip-approval`、`skip-audit` 或语义等价绕过；这仍是内部安全调度，不是公共 CLI。V0.4.1 不新增近似“完成”的替代状态，也不签发文档正式交付状态。

### 6.1 非交付证据生命周期

`execution-evidence-artifact` 的证据等级至少分为 `diagnostic`、`implementation_exit` 和 `delivery`：

- `diagnostic` 记录局部测量、调试、Word 收敛快照或失败原因，不证明版本或文档完成；
- `implementation_exit` 证明某个实现 PR/工作流或 V0.4.1 退出门禁通过，但不证明具体书稿可交付；
- `delivery` 才能参与 V0.4.0 `final_ready` 的正式完成判定。

V0.4.1 的 `execution-evidence-artifact` 只能产生前两类，全部固定 `non_delivery=true`、`final_ready_eligible=false`、`evidence_scope=v0.4.1`；其 schema 直接拒绝 `evidence_class=delivery`。V0.4.1 Word 收敛结果也只是诊断或实现退出参考，不是 `delivery`。不得通过翻转标志、复制文件到另一任务、更新 `capability-snapshot`、改变 `schema_version` 或重新计算 SHA-256，把旧证据升级为 `delivery`。

V0.4.3 建立完整对象台账后，必须重新运行或按后续批准方案重新验证并生成新的 `evidence_id`。新证据可以通过 `supersedes` 引用旧证据，但不得覆盖、改写或原地升级旧证据；它必须重新绑定输入、最终 Profile、结构审批、完整对象台账、能力版本、运行时审批链和 Word 环境。`final_ready` 必须要求后续方案规定的 `delivery` 证据，V0.4.1 在结构上永远无法满足该要求。

## 7. 七个强制工作流与至少九个实现 PR

### 11.1 越级和弱模型测试

- 未生成并批准结构工件时 `apply` 失败；
- 输入、最终 Profile、特性清单或审批工件指纹不匹配时 `apply` 失败；
- `actor_role` 自我声明但无匹配授权引用时审批无效；委托出版社扩域必须阻塞；`project_manager`、`developer` 或 `automated_qa` 试图签发 `qa-approval-artifact` 时由 schema/semantic validator 拒绝并记录 `blocked_qa`；
- P4/P5 应用门禁未闭合时 `finalize` 失败；
- V0.4.1 的 `verify → final_ready` 始终拒绝：即使 `approved=blocked_qa=failed=0`、Word 已收敛，只要完整对象台账/守恒/覆盖 capability 或证据不可用，仍不得产生 `final_ready`；
- `verify` 前后候选 DOCX 字节及允许变化审计均无新增变化；
- P1-P7 测试运行、阶段报告和直接调用构件脚本得到的产物均带 `non_delivery=true`；构件产物不能被状态机接纳为正式前置证据；
- 翻转 `non_delivery`、跨任务复制证据、替换或伪造 `capability-snapshot`、修改 schema/工具版本后重算指纹，以及局部状态归零加 Word 收敛，均不能把 V0.4.1 证据升级为 `delivery` 或取得 `final_ready`；
- 弱模型只获得“当前合法下一阶段”，无法通过参数、旧状态文件或复制工件跳过批准；
- 特性关闭时新 schema、规则、执行器和 Word 集成都不改变现行入口行为。

### 11.2 Word 收敛测试

目标 Microsoft Word 是最终分页声明的唯一后端。测试开始前必须加载并核对 P7 功能基线的全部字段，复现实验步骤并记录环境偏差；任一必填项缺失时硬失败。测试必须覆盖：首次 TOC 导致目录增/减页；页码位数导致目录项换行；正文物理起始页变化但逻辑页仍从 1 开始；不编号区不消耗逻辑前置页；目录承接已编号前置页；PAGE、NUMPAGES、SECTIONPAGES、PAGEREF 与 TOC 页码在第 2 轮收敛；第 3 轮才稳定；三轮后仍变化。

连续两轮必须比较目录条目计数/顺序/文字哈希/页码、目录总页数、正文起始物理与逻辑页、各节起始值/格式、总页数和全部白名单页面字段结果。任一项变化即未收敛。未收敛临时副本不得回写；LibreOffice/PDF 只用于补充排查。

## 15. 残余风险

- 150 项基础决策会扩大注册表和测试体量；P1 必须守住注册表机制和 schema 的单一真源，P2 不得私建规范化表，P3a 只能填充声明式属性条目，P3b 只能建立规则/迁移/追踪资产，不能在 validator 中堆叠第二套属性知识。
- 作用域等价包含分节、角色和对象例外；定义过宽会误覆盖，过窄会产生重复冲突，P2 必须以对抗性作用域测试冻结比较语义。
- 旧 Profile 的同名规则在多个版本中值不同；迁移必须同时绑定源文件指纹和规则 ID，不能只按规则 ID 猜版本。
- python-docx 不能完整表达所有 Word/OOXML 对象；V0.4.1 只能为受支持对象建立执行边界，完整包级分母留给 V0.4.3。
- Word 可重写非目标 XML；P7 的一次性副本、白名单回写和只读重开只能降低风险，V0.4.4 仍需按目标 Word 版本扩大验证。
- 统一入口无法阻止控制宿主或状态目录的调用者执行脚本、改写工件并重算 SHA-256。V0.4.1 的可验证指纹与证据链只能检测普通不一致、陈旧工件和非预期变化，不能提供来源认证或恶意篡改防护；真正数字签名需要后续独立安全设计。
- 运行时 `actor_role` 和授权引用仍依赖任务宿主诚实保存；权限验证防止普通越级和扩域，不提供法律身份认证。运行时审批与项目治理必须保持两条独立证据链。
- P3/P5 即使拆为 P3a/P3b、P5a/P5b 仍可能偏大；进入工作流前必须复核实际文件和测试范围，P5b 无法独立审查时继续拆分。
- P7 功能兼容结果只对冻结的 Windows/Word/语言/字体/打印机/兼容模式环境成立；不能外推为 V0.4.4 千页性能结论。
- 默认关闭会暂时保留旧行为及其已知限制；这是避免部分迁移污染用户稿件的有意取舍，不应被描述为 V0.4.1 已改善现行输出。
- V0.4.1 不设千页性能结论；规则数量、合成时间和 Word 收敛成本必须在 V0.4.4 预先冻结机器和阈值后评估。
