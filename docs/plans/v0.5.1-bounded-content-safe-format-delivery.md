# V0.5.1 内容零改写与格式纵向交付方案

状态：用户已于 2026-09-03 明确批准最终方案；方案 PR 合入 `main` 后生效，合并仍须单独明确授权。

本文件只定义后续开发目标、边界、流程和验收。它不授权实现、提交、推送、PR、合并、发布、私有书稿处理或恢复暂停的 R2 工作。用户批准最终文本并明确授权合并方案 PR 前，产品开发保持暂停。

## 1. 目标、权威与完成定义

### 1.1 唯一产品目标

> 在本地环境中，根据用户批准的任务 Profile 和 V0.4.0 格式语义，对中文专著 DOCX 进行安全、可重复的格式整理；保持作者内容及对象内容和语义结构不变，生成新的 DOCX，并在 Microsoft Word 中完成获批派生字段、分页和视觉验证。

项目以真实可交付书稿为成功标准，不以 Schema、Registry、Matrix、测试数量、哈希数量、支持平台数量或方案数量作为完成标准。

### 1.2 权威关系

本方案获批并合并后：

1. V0.4.0 第 2 节的格式来源与安全原则、第 5 节的格式值和格式语义继续作为格式权威。
2. V0.4.0 第 7 节的整书顺序和第 8.3 节的 Word 字段收敛顺序作为流程参考，按本方案精简执行。
3. V0.5.1 取代 V0.5.0，成为唯一日常开发路线；V0.5.0 保留为历史收敛方案。
4. V0.4.1—V0.4.1.8 继续作为历史设计与证据，其 Registry、Matrix、Ownership、C2、P3b 和后续门禁不再阻塞核心交付。
5. V0.4.0 的六层 Profile、全对象治理台账、不可变状态历史、强制多 PR 拆分和 1000/2000 页基准不自动成为核心实现要求。

格式权威与现行 Skill、Profile 或代码冲突时，执行员不得自行选择；先记录到格式差距清单，由用户决定，未决对象保持原状。

### 1.3 `final_ready`

只有同时满足以下条件才能报告正式完成：

- 原稿保持字节不变，输出为独立新文件；
- 任务 Profile、结构决定和允许变化已经用户批准；
- 当前原稿、任务 Profile、结构批准、输出 DOCX、Word PDF 和视觉证据均通过本次实体绑定与重新核对，不得复用陈旧批准或验收；
- 作者文字、表格内容与结构、图片媒体、图片/表格逻辑位置、公式和复杂对象通过零改写审计；
- 格式符合本次批准范围内的 V0.4.0 规则；
- 序号和派生字段差异完全落在允许变化清单内；
- Microsoft Word 字段刷新、分页和收敛验证完成；
- 在一次性副本中以已验收候选稿作为复验输入，并使用相同 Profile 和批准决定完成语义幂等复验，第二次应用没有产生新的内容、结构、序号、格式或字段漂移；
- 验证 PDF 与 Word 页数一致，全部输出页面完成视觉 QA；
- 本次批准范围和产品声明支持范围内，未解决歧义、处理失败、缺失验证、内容/位置差异和未实现的必需格式规则均为零；
- 明确排除在批准范围外的对象只有在保持未修改、内容/结构/逻辑位置已证明不变且限制已报告时，才可作为非阻断残余；
- 没有私有资料、密钥或页面泄露。

测试、CI 或候选文件均不能单独证明正式完成。

## 2. 产品边界

### 2.1 输入、输出和书稿范围

正式输入限于 DOCX、用户批准的任务 Profile、结构决定和本地目标 Word。正式输出限于：

- 不覆盖原稿的新 DOCX；
- Microsoft Word 生成的本地验证 PDF；
- 不含书稿正文的验收摘要；
- 问题、限制和人工复核报告。

产品面向中文专著和理工科专著。V0.4.0 A—Z 继续定义本项目的目标格式规则。当前实现可能尚未覆盖全部规则，后续按用户可见格式模块分批补齐，不要求在单个版本或 PR 中一次完成。产品只能声明支持已经实现并通过验收的规则；对目标书稿中实际出现但尚未支持的对象，必须保持原状并明确报告，不得宣称完整符合 V0.4.0。

核心范围优先覆盖页面与分节、前置部分、目录与页码、页眉页脚、标题与正文、列表与引文、图片与表格及题注、公式保护、注释、参考文献、附录、Word 派生字段和最终分页。

定义、定理、例题、习题、提示框、代码、索引、术语表等对象，只在批准 Profile 或真实目标书稿出现时进入对应批次；尚未支持的对象保持原状并报告，禁止套用相似格式猜测处理。

### 2.2 平台顺序

1. 第一正式平台：macOS + Microsoft Word for Mac。
2. macOS 纵向路线稳定后，接入 Windows + Microsoft Word。
3. 两个平台复用格式核心、内容保护标准和最小 Word 协议；平台差异仅进入 `adapters/`。
4. LibreOffice 只用于已验证的检查、预览、安全探针或降级诊断，不代替 Word 最终化，不产生 `final_ready`。
5. Linux、WPS、云端 Office 和其他编辑器不是当前发布平台。

Windows 是明确的后续产品平台，但不是 macOS 首个闭环的前置门禁。

### 2.3 默认威胁模型

默认环境为可信本地用户和可信操作系统。核心防护对象是 AI 误操作和普通故障：越权改稿、错误分类、覆盖原稿、路径冲突、部分写入、临时文件污染、未批准结构变化、缺少证据却报告成功，以及私有资料泄露。

保留独立输出、基础路径检查、原子写入、临时隔离、前后内容审计、Word/视觉证据和失败关闭。

同一用户权限下的恶意替换、复杂 inode/文件描述符竞态、加密证据链、签名、任意程序依赖闭包和司法取证式历史属于可选高保障，不是核心门禁，也不得在未获批准时继续扩展。

### 2.4 非目标

当前项目不承担：

- 文字润色、校对、事实核查或内容重写；
- 自动纠正标点、空格、错字、答案或参考文献；
- 封面和插图创作、图片内容处理；
- PDF 反向重建 DOCX；
- 多人协作、云端出版或通用文档管理；
- 同时支持所有系统和文字处理软件；
- 为未知出版社或未来需求预建通用 Schema、Registry 或审批平台；
- 面向恶意本机操作者的安全产品。

未来如需上述能力必须另行立项，不得成为当前路线的隐藏条件。

## 3. 不可覆盖的内容零改写边界

### 3.1 总原则

格式化只能修改获批版式属性。除用户明确批准的序号调整和白名单派生字段结果外，任何作者内容和原有对象都不得增加、删除、替换、改写、重排或改变语义。任何 Profile、模板、标准、脚本参数或 AI 判断均不能覆盖本节。

### 3.2 文字

不可修改可见字符、数字、字母、标点、符号、顺序、段落内容，以及原稿已有的空格、制表符、换行和空段。标题、题注、脚注、尾注、参考文献、答案、超链接文字、书签文字、批注、修订和内容控件文字同样不可修改。

疑似错字、标点、空格或格式模拟问题只能报告。不得以“格式统一”“清理空白”或“提高质量”为由自动修复。

### 3.3 图片和媒体

图片及媒体的二进制内容、格式、关系、数量、顺序和在文中的逻辑位置不可改变。图片必须保留原 story、语义锚点段落或单元格、前后内容关系及对象顺序；禁止替换、删除、复制、压缩、裁剪、旋转、滤镜、重新编码、修改链接目标或改变宽高比。

图片必须按照本次批准的格式要求调整版式，包括等比例显示尺寸、对齐、环绕、所在段落格式、与题注的间距和分页绑定。若格式要求涉及内嵌/浮动形态或定位方式，只能在保持原语义锚点、前后内容关系和对象顺序的条件下调整，并通过媒体哈希、关系和锚点审计。

“位置不变”指图片在文档结构中的锚点、容器、前后关系和顺序不变。其他正文格式变化可能使图片被动出现在不同物理页或页内坐标；系统不得为了固定原页码而移动图片、插入内容或破坏分页。

### 3.4 表格

表格行列数量与顺序、合并关系、单元格文字和对象、表头语义、数据对应关系、嵌套结构及在文中的逻辑位置不可改变。表格必须保留原 story、容器、前后段落关系和块顺序；不得移动到其他章节、段落或容器。

表格必须按照本次批准的格式要求调整边框、底纹、字体、字号、单元格内段距、单元格边距、列宽、行高、整体对齐、左右缩进、浮动/定位和跨页等版式属性，但任何调整都不得改变表格的语义锚点、前后内容关系、块顺序、内容或结构。

不得通过拆分、合并、增删或重排表格实现视觉效果。

“位置不变”同样指表格的文档结构位置不变；其他正文格式和 Word 分页可能使其物理页码被动变化，不得通过移动表格或改写内容强行保持原页码。

### 3.5 公式、字段和复杂对象

- OMML、MathType、OLE、EQ 等公式的表达式和语义不可修改，也不得栅格化。
- 书签、脚注、尾注、批注、修订、文本框、内容控件及嵌入对象不得删除或替换。
- 既有字段指令、边界、书签目标和来源文字不可任意改变。
- 无法验证的对象保持原状并报告。

### 3.6 序号例外

序号调整只限用户批准的对象和编号方案，例如标题、图、表、公式、例题或附录编号。

- 优先使用 Word 编号定义或字段，不直接改写正文。
- 删除或替换原有手工序号属于内容例外，必须在结构批准中明确对象范围、旧形式和新方案。
- 序号后的标题或题注文字不得改变。
- 存在歧义时保持原状并请求用户决定。

### 3.7 派生字段例外

目录条目、页码、总页数、交叉引用显示值等由批准来源机械生成的字段结果不视为作者原文，但只能在以下条件下刷新：

- 字段类型和来源已获批准；
- 既有字段指令、边界、书签目标和来源文字保持不变；
- 只更新白名单字段，禁止无差别 `update-all`；
- 结果由目标 Microsoft Word 生成并通过重新打开验证；
- 差异只出现在预期字段结果范围内。

创建原稿不存在的目录、目录题名或其他派生结构必须另获明确批准；系统不得擅自补写题名、说明或任何作者文字。

### 3.8 版式结构

纸张、页边距、分栏、页眉页脚、页码边界和分节属于版式结构，但新增、删除或移动分节必须在结构决定中明确批准。最终 Word 收敛阶段不得再次改变这些边界。正文、段落、表格、图片和对象顺序始终不可因分节处理而改变。

## 4. 格式规则、Profile 与数据边界

### 4.1 格式来源顺序

同一格式属性按以下顺序确定：

1. 内容零改写和其他安全不变量，不可覆盖；
2. 当前用户明确要求和 QA 决定；
3. 用户指定且允许用于本次任务的出版社规范或 DOCX 模板；
4. 已批准的功能模块，只在自身语义对象范围内生效；
5. 用户选择的书籍类型 Profile；
6. V0.4.0 `monograph-base`；
7. 经确认适用的 GB/T 等公开标准，仅用于以上来源没有覆盖的项目。

内容零改写边界高于所有格式来源。功能模块越界的规则不参与当前对象的格式决议；多个已批准功能模块发生同对象、同属性冲突时进入 QA。同层冲突、来源不明、低置信度或无法分类时，保持原状并报告，禁止按加载顺序或 AI 偏好决定。

出版社要求与适用的 GB/T 基础标准对同一对象、同一属性给出不同要求时，即使出版社来源顺序更高，也不得静默覆盖。系统必须记录双方来源、条款定位、差异和影响并等待用户决定；决定前不批准或应用相关规则，结果写入本次任务 Profile，不回写来源文件。不受冲突影响的规则可以继续整理。

### 4.2 最小任务 Profile

任务 Profile 只表达格式来源、目标软件、启用规则和值、适用对象、用户覆盖与例外、执行方式、序号与派生结构批准、内容保护和允许变化。

除交付 DOCX 和验证 PDF 外，核心路线只保留三类控制/证据工件：

1. 任务 Profile；
2. 结构与批准结果；
3. 执行与验收报告。

不要求每个属性保存完整覆盖历史、生产 Registry 映射、Ownership 或迁移证明。内部临时数据不建立正式 Schema。

### 4.3 现有复杂资产

- 停止新增生产 Registry、Artifact Matrix、Ownership Map 和版本级联 Schema。
- 已合并的 Registry 2.0—2.2 和高保障设施保留兼容，不扩展，也不作为核心完成条件。
- 暂停的 R2 Registry 2.3/Matrix 1.2 不开发、不提交、不推送、不合并；本方案批准后正式退出当前路线，是否归档或删除由用户另行决定。
- 只有真实书稿或目标 Word 失败证明现有结构不足时，才可提出最小增量；扩大边界必须由用户批准。

### 4.4 当前实体的最小绑定

不新增工件或 Schema，只在现有三类控制/证据工件中记录和核对当前实体：

- `prepare` 记录原稿和任务 Profile 的 SHA-256 与大小；
- 结构批准结果绑定当前原稿、任务 Profile 和批准决定的摘要，任一变化使旧批准失效；
- 输出 DOCX 和 Word PDF 记录 SHA-256 与大小，PDF 另记录页数；
- 视觉验收必须绑定同一个 Word PDF 摘要和页数；
- `apply`、`finalize`、`verify` 以及任何显示 `final_ready` 的状态入口，都必须针对当前实体重新核对相关绑定。

运行所需的本地路径只能保存在不进入 Git 的本地控制状态中；公开报告、对话和仓库只使用工件角色、摘要、大小和页数，不保存私有绝对路径。这些绑定只防止普通错用、陈旧状态和单侧文件替换，不构成签名、身份认证或对恶意本机用户的防护。

## 5. 参考 V0.4.0 的轻量整书流程

本节采用用户已确认的“整书分析和确认 → 按章应用格式 → 整书最终化和验收”流程，并与 V0.4.0 保持相同的业务顺序和关键门禁。所有章节始终位于同一受控派生 DOCX 中，不物理拆分后重新拼接。

一致的是格式修改的先后关系、内容保护、结构先批准、字段后最终化、最多三轮收敛和最终只读验收。精简的是全对象治理台账、逐对象不可变历史、每批原子检查点、复杂恢复链和逐属性 Registry 映射；这些不改变格式流程，只有真实长书失败证明需要时才另行提出。

### 阶段 1：任务与环境确认

确认原稿、独立输出、目标 Word、任务 Profile 和私有边界。原稿作为只读输入并记录原稿/Profile 的最小身份；检查必要运行时和 Word 能力，不上传、不公开私有书稿、页面、路径或密钥。

### 阶段 2：整书只读 `prepare`

一次扫描整份书稿，识别前置部分、章节和标题层级、正文、图、表、公式、注释、参考文献、附录、页面/分节、目录、页码、字段和复杂对象。生成结构候选、格式差距、歧义、拟应用规则和允许变化候选，并建立文字、表格、媒体、位置、公式、字段和复杂对象的保护基线；不得修改 DOCX，也不建设全对象治理 Registry。

### 阶段 3：确认语义目录

根据原稿已有文字建立章、节、标题层级、章节边界、目录收录范围、前置/正文/附录归属和序号候选。语义目录只是结构映射，不是正式 Word TOC，也不得修改标题文字。

用户确认语义目录、歧义、格式规则、序号、派生结构和允许变化。批准结果绑定当前原稿、任务 Profile 和决定摘要；其中任一变化都必须重新确认。普通且无歧义的格式属性无需逐项审批；必要批准缺失时保持 `awaiting_structure_approval`，不得应用。

### 阶段 4：确认并应用整书页面/分节

先统一确认纸张、方向、页边距、分栏、前置不编号区、目录/正文页码系统、页眉页脚、章首页和横向页边界，再只对获批版式属性进行处理。此阶段不得移动正文、图片、表格或其他对象。

### 阶段 5：处理书名页和前置部分

处理书名页、版权页、题献、序、前言等已识别角色的版式及其获批页码/分节属性。不得增加、删除、改写或重排前置文字，原稿不存在的题名或说明不得自动补写。

### 阶段 6：正文默认按章 `apply`

按照批准的语义目录逐章处理标题、正文、列表、引文、图片、表格、题注、公式、脚注、尾注和其他获批对象。图片和表格必须留在原锚点、容器、前后关系及顺序中，不得因格式化移动。

每章完成后执行简明的内容零改写和对象位置检查。失败立即停止，不继续下一章，也不把失败候选作为正式输出。所有章节始终位于同一个受控 DOCX；只有实测失败证明需要时才增加复杂恢复或检查点。

### 阶段 7：全书统一调整获批序号

章节基本格式稳定后，统一完成本次任务所有已批准的全书编号和序列域，包括实际出现并获批的标题、图、表、公式、定义、定理、例题、习题、代码、附录及其他对象序列。优先使用 Word 编号或字段；手工序号变化必须符合批准清单，序号后的作者文字不得改变。没有出现或没有批准的序列不处理，也不因示例列出而提前开发。处理后再次执行整书内容差异检查。

### 阶段 8：处理后置部分和跨章关系

处理参考文献、附录、索引等已批准后置对象的版式；验证并保持既有跨章书签、交叉引用和对象关系，只整理其周边获批版式。不得创建、重命名、重定向或改写书签、字段指令和来源关系，也不得修改参考文献或其他后置内容及顺序。获批字段显示结果只在 Word 最终化阶段刷新。

### 阶段 9：生成或更新正式 Word TOC

只有语义目录已批准、所有章节、全部实际获批序列及其交叉引用来源已经完成并通过审计、分节/页码稳定且零改写检查通过后，才生成或更新正式 TOC。既有 TOC 只更新获批结果；原稿没有 TOC 时，创建 TOC 和目录题名必须另获明确批准。目录来源只能是已批准语义标题。

### 阶段 10：Microsoft Word `finalize` 和收敛

在一次性 Word 工作副本中：

1. 以阶段 9 的首次 TOC 结果作为第 1 轮输入，全书重新分页；
2. 选择性更新 PAGE、NUMPAGES、SECTIONPAGES、PAGEREF、获批交叉引用及其他白名单字段；
3. 再次更新 TOC、重新分页和更新白名单字段，形成第 2 轮；
4. 逐项比较完整收敛元组：TOC 条目数量、顺序、每条完整显示文字及页码，TOC 总页数，正文起始物理页和逻辑页码，各节页码起始值和编号格式，文档总页数，以及所有获批 PAGE、NUMPAGES、SECTIONPAGES、PAGEREF、交叉引用和其他页面依赖字段结果；
5. 第 2 轮仍变化时允许第 3 轮，最多三轮。

连续两轮完整收敛元组一致才算收敛。TOC 完整文字在本地内存中逐条比较；持久报告只记录条目数量、顺序和逐条文字哈希，不保存目录文字。这份精简收敛快照纳入现有执行与验收报告，不创建新工件或新 Schema。三轮后仍不一致则 `blocked`，不得猜测、强行回写或报告完成。此阶段不得改变已批准分节、页码方案或字段来源。

### 阶段 11：整书只读 `verify`

验证阶段不得修复、格式化、刷新字段或写回。检查：

- 原稿字节未变；
- 全文文字、空白、段落和顺序；
- 表格结构、单元格内容、逻辑位置和对象；
- 图片/媒体哈希、数量、顺序、关系和逻辑位置；
- 公式、字段指令、书签、关系和复杂对象；
- 序号及派生字段允许差异；
- 批准格式规则；
- Word 字段、页数和重新打开结果；
- PDF 页数及全部页面视觉 QA；
- 在一次性副本中以已验收候选稿作为输入，使用相同任务 Profile 和批准决定再次运行核心格式路线；将第二次输出与已验收候选稿比较，确认没有新的内容、结构、序号或格式变化，并确认 Word 字段结果仍满足收敛条件。

幂等复验比较语义、结构、格式和字段结果，不要求 DOCX ZIP 容器的二进制字节完全相同。任何新的非白名单差异或非预期格式漂移都使候选稿失败，不能进入 `final_ready`。`resume` 和复杂恢复只在相关能力实际存在、被使用或真实长书证明需要时验证，不因幂等门禁而预建恢复框架。

### 阶段 12：交付

交付新 DOCX、验证 PDF 和简明报告。报告格式范围、序号/派生字段变化、内容保护、Word/视觉结果、人工决定和残余限制；不得包含书稿正文、私有页面、私有路径、密钥或迁移资料。

正式入口沿用最小状态：

`prepare → awaiting_structure_approval → apply → ready_to_finalize → finalize → verify → final_ready`

未满足条件时保持候选或 `blocked`。无需为每个对象保存不可变状态历史。

## 6. 后续开发阶段

### P0：批准本方案

用户判断第 10 节决策项；经理按决定修订。最终文本获明确批准后才提交方案 PR；方案 PR 获明确合并授权并合并后，才能恢复产品开发。

### P1：V0.4.0 格式差距审计

对照 V0.4.0、当前 Profile、Skill、代码和测试，按用户可见模块记录“符合、部分符合、未实现、冲突、需真实 Word 验证”。不建立逐属性生产 Registry 或新 Schema 体系。

首先处理已知规则冲突，例如 V0.4.0 要求目录题名“目录”不得用字间空格，而当前 Skill 仍含历史四空格形式。

### P2：macOS 现有路线基线

在干净 `main` 工作树和隔离环境中，使用一个完全合成 DOCX 和一个经用户指定、仅在本地使用的代表性私有书稿，运行现有纵向路线，记录真实格式差距、Word 阻断、内容审计、视觉问题、时间和人工决定。

私有书稿、文件名、路径、页面、密钥和内容不得进入 Git、对话或公共服务。

### P3：macOS 核心修复

只修复 P1/P2 已证明阻止交付的问题，顺序为：

1. 页面、分节、前置部分、标题和正文；
2. 目录、页码、页眉页脚和 Word 最终化；
3. 图片、表格、题注和公式保护；
4. 注释、参考文献、附录及真实书稿出现的其他对象；
5. 内容零改写与逐页验收闭环。

每个批次必须形成用户可见结果，不得以修复为名建立新框架；尚未出现的格式类型不提前实现。

### P4：长书稳定性

macOS 闭环通过后，用一份代表性长书测量耗时、内存、Word 收敛和中断影响。只有测量证明需要时才增加批处理、恢复或性能优化，不预设 1000/2000 页硬门禁。

### P5：Windows Word 适配

复用稳定的格式核心、内容保护和最小 Word 协议接入 Windows，不重新设计 Profile、Schema 或格式引擎。真实 Windows Word 字段、分页、PDF 和零改写验收通过后，才能宣称支持。

### P6：发布判断

提供一个真实候选、简明验收摘要、一次独立整体审查和用户发布决定。PR 合并不自动等于发布授权。

## 7. 测试与验收

每个完整开发批次执行：

- 直接相关的合成测试和回归测试；
- 注入非白名单文字、图片、表格或对象变化时必须失败；
- 代表性真实书稿的本地差异和视觉验证；
- 必要的目标 Word 实机验证；
- 正式候选的一次语义幂等复验；
- PR CI、基本静态检查和私有信息检查。

内容审计使用精简的前后清单和可理解差异，覆盖各 story 的文字/空白/顺序、表格、媒体、公式、OLE、内容控件、批注、修订、字段和书签。只要整书覆盖和允许差异可证明，不要求使用 Registry、Ownership 或不可变对象历史。

不要求每次小修重复高保障、全平台和大规模性能测试。真实目标环境结果不能被测试数量代替。

## 8. 角色与审查

- 用户决定产品范围、格式取舍、结构歧义、方案、PR 合并和发布。
- 项目经理制定边界明确的任务、管理依赖、独立进行经理审查，并汇总执行员和审查员结果；不开发产品代码，也不把经理审查结论发送给独立审查员。
- 执行员只实现批准任务并自测，只向经理报告，不联系审查员，不扩大范围。
- 独立审查员只向经理报告，在完整批次结束后审查一次，不联系执行员，也不接收经理结论。

默认流程：

`用户批准批次 → 经理下达任务 → 执行员实现/自测 → 经理内部审查 → 独立审查员整体审查 → 阻断项成批修复并限定复核 → 经理汇总 → 用户决定合并`

不为每个小问题重复整体审查。只有安全边界、方案、正式平台或重大架构变化，以及完整批次结束时，才安排独立整体审查。

## 9. 防止过度开发的停止条件

任何新机制进入开发前必须回答：

1. 哪个真实书稿、目标 Word 运行或现有测试暴露了问题？
2. 它是否直接阻止当前批次的用户可见结果？
3. 现有 Profile、结构决定、报告字段或代码为什么不足？
4. 最小直接修复是什么？
5. 新增后可删除、停用或简化什么？
6. 是否扩大产品、平台、数据或威胁模型？

缺少第 1 或第 2 项，不进入开发。以下情况必须停止并交用户决定：

- 新 Schema、Registry、Matrix、Ownership 或正式工件类型；
- 新平台成为发布门禁；
- 新公共 CLI/API 或安装产品化；
- 新高保障/对抗性协议或大范围重构；
- 私有资料需要进入 Git、对话或公共服务；
- 内容零改写边界或 V0.4.0 格式值需要变化；
- 单个缺陷被扩展为通用框架。

执行中发现优化项时，经理只提交收益、成本和风险，由用户决定，不默认纳入。

## 10. 用户已批准的决策

以下决策已随最终方案于 2026-09-03 获用户明确批准；不因此自动授权产品实现、PR 合并或发布。

1. **内容边界**：文字、表格内容与结构、图片媒体、公式和复杂对象绝对不改；只有获批序号和派生字段结果属于内容差异例外。
2. **图片/表格版式与位置**：图片和表格必须保留原 story、语义锚点或容器、前后关系及对象顺序，同时按照本次批准的格式要求调整尺寸、对齐、环绕、间距、边框、宽度、跨页等版式属性。绝不改变图片内容、表格内容/结构或把对象移动到其他正文位置；正文重排导致物理页码被动变化不视为移动对象。
3. **派生字段**：允许 Word 按白名单刷新目录页码、PAGE、NUMPAGES、SECTIONPAGES、PAGEREF、获批交叉引用和其他逐项获批的页面依赖字段；创建原稿不存在的目录等派生结构仍须单独批准。
4. **格式权威**：V0.4.0 第 2、5、7 和 8.3 节承担格式语义与流程参考，其复杂长期架构不作为核心门禁。
5. **平台顺序**：先完成 macOS + Word，再接入 Windows + Word；LibreOffice 不承担正式最终化。
6. **Schema 收敛**：停止 Registry/Matrix/Ownership 扩展，只保留任务 Profile、结构批准和执行报告三类核心持久工件。
7. **R2 处置**：Registry 2.3/Matrix 1.2 正式退出当前路线，暂时本地保留，稳定后再决定归档或删除。
8. **审查节奏**：每个完整批次只做一次独立整体审查；阻断项成批修复后只复核影响范围。
