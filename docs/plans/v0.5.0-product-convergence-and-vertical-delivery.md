# V0.5.0 Product Convergence And Vertical Delivery

Status: planning candidate. This document does not authorize implementation,
commits, pushes, pull requests, merges, releases, private-asset movement, or
changes to paused R2 work.

## 1. Purpose

The current product goal is one reliable, user-visible monograph formatting
loop:

> Given an approved format profile and a DOCX manuscript, produce a new DOCX
> that applies the approved formatting without changing author content, then
> finalize fields in Microsoft Word, audit the result, render it, and report
> any unverified or ambiguous condition honestly.

V0.5.0 converges the implementation route around that outcome. It does not
discard earlier work, but it stops treating every long-term platform,
formal-proof, and high-assurance objective as a prerequisite for the current
product.

## 2. Authority And Supersession

After this plan is accepted and merged, it is the sole day-to-day
implementation route. V0.4.1 through V0.4.1.8 remain immutable historical
evidence, but their unfinished sequencing, registry-succession, ownership,
matrix, C2, P3b, and later-stage gates no longer block the core vertical
delivery route.

V0.4.0 and the approved Profile assets remain the authorities for format
values and formatting semantics. V0.5.0 governs only the implementation route
and current product boundary.

This supersession does not:

- change previously approved format values;
- delete or silently rewrite merged code or tests;
- weaken the safety invariants in section 5;
- revive a rejected candidate or authorize paused R2;
- claim that an unverified platform or backend is supported;
- turn historical planning evidence into runtime product state.

Any future high-assurance work must receive separate scope approval and must
not become a hidden prerequisite for the core route.

## 3. Supported Product Boundary

### 3.1 Primary supported environment

- macOS;
- the repository's pinned project Python runtime;
- Microsoft Word for Mac for final field, table-of-contents, pagination, and
  verification evidence;
- Codex Desktop using the repository's normal skill entry.

LibreOffice is limited to inspection and safety-smoke paths that existing
evidence has explicitly validated; every other use remains deferred. It must
not claim Word field completion or final-ready status. Windows and other Agent
Skills-compatible hosts remain compatibility directions, not current release
gates.

### 3.2 Default threat model

The default environment is a trusted single user working in a local project
directory. Core protections cover accidental overwrite, partial failure,
incorrect formatting, content drift, unsupported objects, and false success
claims.

Adversarial same-user filesystem replacement, hostile runtime mutation,
cryptographic evidence chains, and equivalent system-level attacks belong to
an optional high-assurance mode. Existing protections are not deleted merely
because they exceed the default threat model, but extending them cannot block
the core route without new user approval.

## 4. Capability Layers

### 4.1 Core delivery

Core delivery owns only:

- approved Profile ingestion and rule precedence;
- DOCX structure identification needed by the approved Profile;
- formatting of pages, sections, headings, body text, tables, images,
  captions, equations, and other explicitly supported objects;
- pre/post content and protected-object audit;
- Microsoft Word field and pagination finalization;
- rendered visual QA and a concise delivery report;
- creation of a new output without overwriting the source.

### 4.2 Long-document enhancement

Long-document enhancement may add bounded batching, resume, idempotency,
whole-book consistency checks, and recovery. These features must serve a
measured long-document failure or runtime need and must not create a parallel
approval system.

### 4.3 Optional high assurance

High assurance may contain adversarial publication protocols, extended
artifact binding, formal registry closure, exhaustive ownership evidence, and
broader cross-platform proof. It is disabled as a core completion gate and
requires separate authorization, acceptance criteria, and evidence.

## 5. Non-Negotiable Safety Invariants

Every layer must preserve all of the following:

- never overwrite the source manuscript;
- never change author facts, wording, answers, references, or equation
  semantics as part of formatting;
- never rasterize an editable equation merely to make rendering easier;
- never silently substitute fonts or unsupported objects;
- preserve unknown or ambiguous content and report it;
- compare author content, equation semantics, fields, relationships, media,
  and protected objects before and after formatting across the whole document;
- choose comparison techniques in proportion to the reachable modification
  surface, but never replace whole-document integrity coverage with sampling or
  limit it to objects the formatter claims to have touched;
- fail closed when required Word, audit, render, or visual evidence is absent;
- never report deferred, candidate, or partially verified output as final;
- keep private manuscripts, keys, migration packages, and rendered private
  pages out of Git and public services.

## 6. Current Asset Disposition

### 6.1 Preserve and use

Keep the existing Profile separation, structure mapping, formatting engine,
content/object audit, whole-book runner, Word finalization, rendering, visual
QA, safe-output behavior, and the synthetic tests that exercise them.

### 6.2 Pause, do not merge

The current uncommitted R2 registry 2.3/matrix 1.2 work is paused experimental
work. It is not a candidate and must not be completed, committed, pushed, or
merged under the old route. It may be archived locally for later evaluation.
No part of it becomes core merely because its internal tests pass.

### 6.3 Retain without extending

Merged registry 2.0-2.2, existing evidence machinery, and stronger publication
protections remain available for compatibility. Do not extend them unless the
vertical delivery route demonstrates a concrete missing contract.

### 6.4 Defer

Defer new registry or matrix versions, new artifact types, atomic ownership
maps, public CLI productization, formal approval state machines, simultaneous
full platform support, and broad refactors not required by a measured vertical
failure.

## 7. Architecture Rules

1. Prefer an existing Profile field, report field, or test before adding a new
   Schema, registry, artifact, role, or gate.
2. A new mechanism must identify what it replaces, why existing structures
   cannot express the need, and what is removed or simplified in return.
3. Machine-generated inventories belong in machine files, not Markdown plans.
4. Planning documents define outcomes, boundaries, and evidence; they do not
   embed generated mappings or reproduce historical plans.
5. Large modules are split only along observed responsibility boundaries and
   only when the split is needed for the next approved vertical task. A split
   must preserve behavior and may not become a rewrite.
6. Test count, mapping count, hashes, and green CI are evidence, not product
   completion. A real target-environment result remains required.
7. Unknown requirements produce a reported limitation or a user decision;
   they do not automatically create a new framework.

## 8. Simplified Roles And Workflow

- The user owns product scope, trade-offs, merge authorization, and release
  authorization.
- The project manager writes one bounded task, defines acceptance criteria,
  tracks dependencies, and summarizes evidence. The manager does not implement
  product code or impersonate independent review.
- The executor implements only the approved task and supplies self-test
  evidence. Scope expansion is a stop condition.
- The independent reviewer reviews a completed bounded change once. Blocking
  findings are repaired as one batch; re-review is limited to changed findings
  and their impact surface.

The default route is:

`user scope -> manager task -> executor implementation/self-test -> risk-based
independent review -> manager summary -> user merge decision`

Mechanical implementation steps do not require repeated user approval. Scope,
safety-boundary, external-side-effect, or acceptance-standard changes do.

## 9. Converged Delivery Sequence

### S0: Freeze and inventory

- keep paused R2 and unrelated governance drafts uncommitted and isolated;
- record the exact main commit and currently merged capabilities;
- select one representative private manuscript locally and synthetic public
  fixtures; never commit or quote private content.

### S1: Baseline the existing vertical route

Run the existing Profile-to-delivery path without adding infrastructure.
Record supported structures, manual decisions, elapsed time, failures, Word
evidence, audit findings, and visual-QA findings.

### S2: Repair only observed blockers

Create small, bounded tasks for failures that prevent the vertical result.
Prefer direct fixes and existing contracts. Every proposed Schema, artifact,
or framework addition requires separate user approval.

### S3: Demonstrate long-document reliability

Repeat the accepted route on a representative long manuscript. Exercise resume
and recovery only where the run shows a real need. Do not require optional
high-assurance or experimental-platform completion.

### S4: Release decision

Produce one candidate, one evidence summary, one independent review, and one
user merge decision. Release authorization remains separate.

## 10. Acceptance Criteria

The converged route is acceptable only when:

1. the source remains byte-identical and the output is a separate file;
2. the approved Profile is the only formatting authority used by the run;
3. supported structures are formatted as approved and ambiguous structures are
   preserved and reported;
4. content, equations, relationships, media, fields, and protected objects pass
   a whole-document pre/post no-drift audit;
5. Microsoft Word finalization and no-save verification complete when fields
   require Word;
6. rendered pages and visual QA cover every output page, with no hidden failure;
7. when retry/resume is present or exercised, it does not duplicate or drift
   accepted formatting;
8. the result, elapsed time, manual interventions, limitations, and residual
   risks are reported in plain language;
9. the change contains no private assets and no unapproved platform or
   high-assurance expansion;
10. focused tests, relevant regression, full non-C2 tests, and PR CI pass, but
    none substitutes for the real vertical evidence above.

## 11. Stop Conditions

Stop and return to the user when a task would:

- change the product goal, primary environment, or default threat model;
- weaken a safety invariant;
- require a new public interface, registry version, artifact type, approval
  state machine, or formal platform commitment;
- require private data to enter Git, chat, or a public service;
- convert optional high-assurance work into a core prerequisite;
- turn a bounded repair into a broad architecture rewrite.

## 12. Rollback And Non-Claims

Rejecting or rolling back V0.5.0 leaves `main` and all historical plans intact.
Paused R2 remains non-candidate local work until the user separately chooses to
archive or delete it. This plan does not claim that the current product is
release-ready, that every monograph type is supported, that LibreOffice equals
Microsoft Word, or that the default mode withstands a hostile local operator.
