# V0.4.1.5 Append-Only Production Registry Succession

Status: docs-only planning candidate. This plan assigns no lifecycle state before the named files and tests are actually merged.

## 1. Purpose And Non-Downgrade Rule

V0.4.1.2 permitted P3a-R to fill property registry 2.2. P3a-C subsequently committed property-registry.v2.2.core.json, generated 2.2 artifacts, route/fingerprint behavior, and C1 tests as an internal_committed contract. V0.4.1.4 prohibits changing the legal instance set, canonical bytes, or fingerprint of a committed version in place. P3a-R therefore cannot complete 2.2 in place, nor create a side registry that the later formal chain does not consume.

This plan resolves that conflict only through an append-only successor. It does not reduce format capability, non-performance gates, strict rejection, determinism, privacy, coverage, or future performance proof. Reducing a phase claim or moving proof to its correct stage is not reducing the proof required.

V0.4.0 remains the only authority for the 171 format decisions and their format values. The 150/20/1 ownership split is unchanged. 171/171 means trace disposition is complete; it never means all decisions are implemented, vertically validated, or released.

## 4. 2.2 To 2.3 Replacement Inventory

Before P3a-R implementation, its task must define a machine-checkable replacement inventory covering every item in the 2.2 core categories: properties, data types, units, normalizers, comparators, capabilities, and constraints. Every row records preserve, replace, or intentionally_absent, the source ID, target ID when applicable, rationale, and the verifying test.

Safety invariants may not be omitted. Synthetic intent probes may not enter the production base without explicit classification. The inventory must reject unexplained probes, latest, automatic upgrades, and read-compatible substitution. It must bind new and old loaders explicitly, preserve old 2.2 fixture/golden/fingerprint/C1 tests unchanged, and establish independent 2.3 fixtures and fingerprints.

P3a-R must merge 2.3 once at full_production; it may not continue filling it later. P3b-B and P3b-O must bind exact registry ID, version, completeness, and fingerprint, rather than infer a compatible registry.

P3a-R does not add common, an artifact schema/route/matrix, composer work, global canonical inventory, base rules, runtime entrypoints, or benchmark work. profile_v2_canonical.py is outside the default boundary; a parser gap is a CONTRACT_GAP/STOP, not a reason to expand the task.

### P3b-B: Freeze The Formal Artifact Chain Before Assets

Before creating any first-batch rule or migration asset, P3b-B freezes common 2.4, layered-rule 2.3, feature 2.3, conflict report 2.4, QA 2.3, final profile 2.4, migration 2.2, matrix schema/contract 1.2, formal validator routes, and an independent fingerprint inventory. It proves cross-artifact behavior, default-closed behavior, strict rejection, candidate consumption, conflicts, determinism, privacy, and old-path regressions. Only then may it create first-batch rule/migration assets and partial trace, then close the existing non-performance composer contract.

P3b-B contract and assets form one logical phase. A later task may use one atomic PR or two strictly serial PRs chosen for reviewable size, but may not create independently mergeable branches that lose the required order.

### P3b-O: Consume, Do Not Mutate

P3b-O consumes only the frozen registry 2.3 and matrix 1.2. It completes the base, migrations, trace, and the approved real-base benchmark. It must not modify 2.3, 2.4, or 1.2 in place. A discovered contract deficit stops and requires a separately approved append-only successor, such as matrix 1.3.
