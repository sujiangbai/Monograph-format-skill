# format-monograph V0.2.4：字段终稿化、稳定审计与分页绑定

## 背景与目标

V0.2.3 的真实单章试排验证了人工图表编号、领域图纸标识和确认式改号，但也暴露出终稿阶段仍需临时补丁：新建目录只有字段代码而没有可靠缓存结果；字段更新会改变段落位置并使基于固定序号的审计误报；静态目录残留、大纲级别污染、图表题分页和复杂表头重复需要额外处理；不同排版软件的页数可能不一致。

V0.2.4 将这些通用能力迁入开放 Skill，使单章和整书都使用同一条可恢复、可审计的终稿流程。迁移的是通用行为，不提交真实书稿、试排结果、本地路径、Word COM 或平台私有调用。

## 能力边界

1. 当前调用者的明确格式要求和后续 QA 决定继续具有任务内最高优先级。
2. 原稿永不覆盖；字段刷新、目录替换和分页控制只写入派生稿。
3. 正文、表格文字、注释、引用、答案、公式和媒体对象继续受完整性保护。
4. 图表编号默认保持人工可编辑文字；本方案不改变 V0.2.3 的 `SEQ`、领域图纸标识和确认式改号规则。
5. 核心脚本必须跨 Windows、macOS 和 Linux，不依赖 Word COM、PowerShell、Agent 私有 API 或绝对路径。

## 终稿工作流

在现有盘点、结构确认、格式应用和初次审计之后增加正式终稿阶段：

```text
finalize_docx.py <formatted.docx>
  --profile <format-profile.json>
  --structure-map <approved-structure-map.json>
  --output <finalized.docx>
  [--field-updater auto|libreoffice|deferred]
  [--renderer <path>]
```

终稿阶段必须：

1. 重新验证输入稿、配置和结构映射的绑定信息。
2. 执行已批准的目录清理、字段刷新和分页绑定。
3. 保存为新的 DOCX，不覆盖格式应用阶段的中间稿。
4. 生成字段状态和终稿操作清单。
5. 使用稳定内容流重新审计源稿与终稿。
6. 逐页渲染终稿；每次布局修复后重新审计和渲染。

`apply_profile.py` 负责确定性的格式和 OOXML 结构变更；`finalize_docx.py` 负责可能改变字段缓存和分页结果的终稿操作。两者不得把未经批准的临时启发式写入文档。

## 字段刷新与状态

### 字段状态

盘点和报告区分：

- `absent`：没有目标字段。
- `code_only`：存在字段代码，但没有可交付的缓存结果。
- `stale`：缓存结果存在，但标题或分页已变化。
- `refreshed`：本次通过受支持的字段后端完成刷新并重新保存。
- `deferred`：只设置打开时更新，尚未验证显示结果。

不得把 `code_only`、`stale` 或 `deferred` 描述为“目录和页码已更新”。

### 跨平台后端

1. `auto` 优先使用可调用的 LibreOffice UNO 接口更新文档索引、目录、交叉引用和页码字段，然后保存派生副本。
2. `libreoffice` 在 UNO 更新不可用或刷新失败时阻塞终稿交付，并报告失败对象。
3. `deferred` 只设置 `w:updateFields`，属于结构模式；必须获得调用者同意，报告中注明未完成字段显示值和视觉验收。
4. 平台适配层可以提供安装与发现说明，但不能改变字段完整性和验收标准。

刷新后必须确认主 `TOC` 指令数量、目录级别、条目数量、`PAGEREF`/`PAGE` 等派生字段状态，并禁止将目录内部页码引用误计为多个目录。

## 稳定结构定位与终稿审计

结构映射升级为 `1.3`，读取端继续兼容 `1.0` 至 `1.2`。固定段落序号只作为源稿定位提示，不再作为终稿中的唯一身份。

稳定定位器包含：

- 源稿内容指纹和所在部件。
- 元素类型、原始顺序及文本或对象哈希。
- 前后非空语义元素的上下文哈希。
- 表格、行、单元格和段落的分层哈希。
- 已批准派生范围的操作 ID。

终稿审计构造规范化内容流：忽略批准生成的目录缓存文字、页码显示值和允许变化的字段结果，但保留并比较正文、表格文字、注释、引用、答案、公式 XML、嵌入对象和媒体载荷。人工标识替换仍只允许逐项批准的精确替换。

审计至少执行两次：格式应用后、字段终稿化后。任一次内容或受保护对象不一致都阻塞交付。

## 静态目录与大纲清理

1. 只删除结构映射中已批准且哈希完全匹配的静态目录范围。
2. 删除前保留源稿审计证据，不在终稿中保留折叠的空锚点段落。
3. 段落 0、书名、前置页和正文起始对象必须单独定位，不能通过固定的“第 41 段”等任务特定序号推断。
4. 只有获批标题保留 `Heading 1` 至 `Heading 4` 或对应大纲级别。
5. 纯图片段落、图题、表题和普通正文若继承标题样式或 `outlineLvl`，应按已批准角色清除污染，防止图片或正文进入目录。
6. 清理后检查目录条目只来自批准标题，并检查正文起始页及尾部空白页。

## 分页绑定与表格行为

结构映射 1.3 增加可逐项批准的 `pagination_groups` 和表格分页属性：

- `figure_with_caption`：图片段落与其图题尽量保持同页。
- `table_caption_with_table`：表题与后续表格保持相邻。
- `keep_rows_together`：图片布局表或普通短行不跨页拆分。
- `repeat_header_rows`：重复连续的表头行。
- `repeat_caption_with_header`：表题位于第 0 行、表头位于第 1 行时，允许连续重复两行。
- `allow_oversize_row_split`：单行高于可用页面时允许拆分并报警，避免无法分页。

分页组使用稳定定位器和对象哈希。不得仅凭相邻位置绑定；角色不明确或图表之间存在正文时生成 QA。图片布局表可以只批准分页保护，不套用数据表字体和边框规则。

## 渲染器差异与可恢复执行

1. 报告记录字段刷新器、渲染器、版本、页数和目标软件。
2. 当目标软件与实际渲染器不同，报告标记 `target_layout_unverified`；不能把等效渲染器结果描述为目标软件实机验收。
3. 同一稿件经多个渲染器得到不同页数时，列出差异并以调用者指定的目标软件为最终判断依据。
4. 工作流状态文件只保存源稿、配置、结构映射和输出的哈希、阶段状态及错误摘要，不保存正文。中断后只有哈希完全匹配才能续跑。
5. 终稿交付前必须确认无尾部空白页、无重叠、截断、缺字、孤立图表题或异常跨页表格。

## 脚本与文档变化

- 新增 `scripts/finalize_docx.py`，提供字段刷新、终稿分页操作和状态清单。
- 扩展 `_common.py`，提供稳定定位、规范化内容流和包载荷哈希工具。
- 扩展 `inspect_docx.py`，识别字段缓存状态、标题大纲污染、分页组候选及布局表分页风险。
- 扩展 `structure_map.py` 和 `validate_structure_map.py`，支持结构映射 1.3。
- 扩展 `apply_profile.py`，执行获批的目录范围删除、大纲清理、表头连续重复及分页属性。
- 扩展 `audit_docx.py`，支持字段展开后的稳定终稿审计。
- 扩展 `render_docx.py`，记录渲染器身份、页数和目标软件差异。
- 更新 `SKILL.md`、`structure-map.md`、`capability-levels.md` 和 `qa-and-reporting.md`，加入终稿阶段与降级规则。

本地试排使用的任务专用脚本不直接复制到仓库；所有硬编码路径、段落序号、表格序号和书稿信息必须删除，由结构映射 1.3 和配置驱动。

## 测试与验收

使用完全合成的 DOCX 覆盖：

1. 静态目录安全删除并生成真实 `TOC`，书名和正文起始内容不丢失。
2. 目录刷新后段落位置变化，终稿审计仍通过；任意正文改字必须失败。
3. 目录内部多个 `PAGEREF` 只归属一个主 `TOC`。
4. 纯图片段落带错误标题样式时不进入目录。
5. 一级至四级标题数量和目录级别与批准结构映射一致。
6. 图与图题、表题与表格分页绑定正确。
7. 表题首行与第二行表头按批准策略连续重复，且表格文字不变。
8. 图片布局表只应用分页保护，不误套数据表格式。
9. 超高表格行允许拆分并产生警告，普通短行不拆分。
10. 媒体、OMML、MathType/OLE、脚注、尾注和表格文字哈希保持一致。
11. 字段后端不可用时正确降级为 `deferred`，未经 QA 不得声称终稿完成。
12. LibreOffice 字段刷新和逐页渲染测试通过；没有目标软件实机能力时正确标记未验证。
13. 中断恢复只在全部输入哈希一致时继续。
14. Windows、macOS、Linux、四个首批 Agent、Agent Skills 规范及全部既有测试继续通过。

真实书稿仅用于用户本地验收，不进入测试夹具、日志、Actions 工件或 PR 描述。

## 实施顺序与治理

1. 从最新 `main` 创建 `plan/v0.2.4-finalization-stable-audit`，新增本方案并更新索引。
2. 方案 PR 经 QA 和用户明确批准后 squash merge。
3. 从新的 `main` 创建 `skill/finalization-stable-audit-v0.2.4`，按本方案迁移通用补丁能力并增加合成测试。
4. 实现 PR 经完整 QA 和用户明确批准后 squash merge。
5. 使用合并后的 V0.2.4 在用户本地重新处理单章，验证结果与已验收稿一致或更好。
6. 单章回归通过后，用整本书执行一次性结构映射、格式应用、终稿审计和逐页检查。

任何后续变化必须新建更高版本方案，不得覆盖本文件。
