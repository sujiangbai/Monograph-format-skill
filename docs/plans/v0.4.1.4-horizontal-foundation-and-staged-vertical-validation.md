P3b-B's merge and exit gates. Every stage starts from the then-current remote

## 4. Revised staged DAG and decision claims

### 4.1 P3a-R: horizontal registry and capability truth

P3a-R may establish the complete registry, constraints, capability map, and
machine-checkable planning projection while C2 performance is unresolved. It
must not claim C2 pass, whole-P3a pass, or executor implementation. A
capability without an executor remains unimplemented.

Audit acceptance is not a technical substitute. The then-current remote main
must contain and pass P3a-C's version route, intent/strict-context isolation,
canonical/fingerprint behavior, coverage conservation, privacy, and old-path
regression. Only the synthetic performance/support-limit STOP is deferred.

### 4.2 P3b-B: default-closed first-batch assets

P3b-B may establish first-batch default-closed assets only after P3a-R merge
and non-performance exit. It may not enable assets, put them in a runtime entry
point, claim DOCX behavior, or consume the deferred real-base gate.

### 4.3 P3b-O: complete base and decisive JSON integration

P3b-O may start only after P3b-B merge and non-performance exit. Its sequence
is complete-base asset-freeze commit, approved versioned benchmark contract,
then benchmark evidence; any asset or contract blob change invalidates that
evidence. The 150 V0.4.1 decisions may enter base implementation; the 20
V0.4.2 and one V0.4.3 remain future-primary/protected and generate no V0.4.1
appearance rules. P3b-O must satisfy the versioned real-base benchmark contract
in section 5 before P4.

The four independent status fields are `trace_coverage`, `implemented`,
`vertically_validated`, and `released`. 171/171 trace coverage implies none of
the other three.

### 4.4 P4 through V0.4.4

- **P4** validates basic DOCX objects vertically: content zero modification,
  target closure, idempotence, and programmatic/supplementary reproducible
  rendering. It is not target-Word field, pagination, or visual acceptance.
- **P5a/P5b** validate complex objects and protection: images, tables,
  captions, fields, OLE, media, formulas, and relationships.
- **P6** closes unified entry, approvals, object state, evidence, and
  anti-bypass behavior.
- **P7** freezes the target Word environment and validates field convergence,
  page-number/TOC final ordering, and a page inventory plus per-page visual
  gate for every page of every versioned whole-book fixture. Manual sampling is
  supplementary only; it cannot replace the per-page gate. V0.4.4 retains its
  full 1000/2000-page visual responsibility. No incomplete work may claim a
  whole-book pass.
- **V0.4.3/V0.4.4** require object ledger, batch recovery, coverage closure,
  and idempotence before 1000/2000-page proof. Long-document success cannot be
  claimed early.

## 5. Versioned real-base benchmark contract

Before P3b-O benchmark work is dispatched, a separately versioned real-base
benchmark contract must be formed and approved. Its absence is a
`CONTRACT_GAP`/`STOP`; it cannot be designed during a benchmark run. It creates
a new config/envelope/version and never modifies the old synthetic config in
place.

Within one approved real-base contract, all compared inputs, environments, and
timing bases are frozen. The new real-base values are not claimed directly
comparable to old synthetic values. It retains the 60/120 wall, RSS, ratio,
66/104, seed/repetition, determinism, conservation, and support-limit gates.

- **1.0x** binds the complete monograph-base commit/tree, canonical inventory
  and digest, and every asset.
- **0.5x** may deterministically reduce counts, but retains every object
  category and rule/binding/scope category. The four topology matrix scenarios
  collectively cover all four topologies; no single cell need contain all four.
  The contract freezes canonical ordering, deterministic rounding, remainder
  distribution, minimum category coverage, requested scale, achieved scale, and
  every exclusion. Sparse categories that cannot hit exact 0.5x record their
  deviation; difficult categories cannot be silently omitted. The precise
  rounding algorithm is selected only after the contract proves it against the
  real inventory.
- **1.5x/2.0x** use deterministic copying/expansion and stable-ID rules without
  changing source-rule semantics.
- The four topologies derive from real base plus a benchmark-only controlled
  intent overlay. The overlay never enters the delivered base and does not edit
  old synthetic assets.

The retired, unavailable old-H formal-scale oracle remains **not proved** and is

- exact canonical bytes/fingerprints for retained route/golden cases;

unavailable old-H formal-scale bytes equivalence. "Oracle unavailable is STOP"

## 8. PR #43 audit, lifecycle, and authorization

PR #43 audit acceptance is a mandatory entry. A per-file audit report must hold
immutable path plus digest, `adopt`/`reimplement`/`drop`, dependencies, tests,
and reason. Project manager and independent reviewer both review it, then the
user explicitly accepts it. Its path/digest and user acceptance record must be
included in the P3a-R/recovery task. Without all of them no recovery or
implementation branch is created. Byte-identical adoption inherits no pass
claim and is retested from new main. PR #43 status remains a separate user
decision.

The lifecycle has exactly four states: `experimental_unmerged`,
`internal_committed`, `compatibility_promised/released`, and `retired`.
`retired-experimental` is the historical audit label for
`experimental_unmerged -> retired`; it is not a fifth compatibility level.
State changes require task proposal, project-manager plus independent review,
user approval, and an append-only plan/decision entry.

On main, every version referenced by a route, fixture, golden, fingerprint, or
historical test is at least `internal_committed`. Such a version must not change
its legal instance set, canonical bytes, or fingerprint in place. A successor
uses a new version and explicitly supersedes it. Its replacement inventory lists
source/target, route, fixture/golden inventory, fingerprint effect, migration,
rollback, and old read path.

After `internal_committed -> retired`, old readers, fixtures, goldens, and
evidence remain reproducible. Default route generation is removed only through
a new version and separate gate; silent deletion is forbidden.

Merging this plan authorizes planning only. It does not authorize recovery,
implementation, benchmark, Word automation, CLI wrapping, Ready, merge,
enablement, or release. Maintain one implementation and one review worktree,
use a current context pack and risk-driven tests, and do not create temporary
runners, manifests, sidecars, or state machines without separately approved
contract-gap work. Public CLI wrapping still needs full capability, multi-round
tests, and final user confirmation.
