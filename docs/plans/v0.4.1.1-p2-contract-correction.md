# format-monograph V0.4.1.1：P2 契约修订附录

## 1. 定位、基线与适用范围

本附录从 `main@52010c4c53cdcfc578a5f3335c59a01304045468` 建立，版本号为 **0.4.1.1**。它是 V0.4.1 的 P2 契约修订附录，高于 V0.4.1，但不占用既定的 V0.4.2 书籍类型扩展版本。

V0.4.1 方案仍是不可变历史快照。凡本附录明确列出的冲突条款，后续 P2 和相关 P6 实现以本附录为规范性权威；未被本附录修订的 V0.4.0、V0.4.1 条款继续有效。

本方案只修订工件依赖、版本路由、权威层级、候选语义、作用域代数及 P2 实施切片，不实现 Schema、JSON fixture、Python、测试、Profile、Skill、DOCX、运行入口或 CLI，也不启用、发布任何能力。

以下治理事实保持不变：

- V0.4.0 已确认的全部格式值和安全不变量不变。
- 当前用户/任务明确要求与后续 QA 决定仍是可覆盖格式层的最高权威；安全不变量不可覆盖。
- V040 决策仍为 171 个唯一 ID，主责统计仍为 `150/20/1`，本附录不新增、删除或迁移这些决策的主责版本。
- 八类运行工件保持不变，不新增第九种 `artifact_kind`。
- V0.4.2 仍负责书籍类型和领域模块，V0.4.3/V0.4.4 的对象台账、恢复和长文验收边界不变。

## 3. 八类工件与无环生命周期

### 3.1 工件数量不变

八类独立工件继续为：

1. `layered-rule-asset`
2. `final-execution-profile`
3. `qa-approval-artifact`
4. `legacy-migration-manifest`
5. `feature-activation-manifest`
6. `capability-snapshot`
7. `conflict-report`
8. `execution-evidence-artifact`

`conflict-report` 的新版标题和职责固定为 **composition proposal and conflict report（组合提案与冲突报告）**，但 `artifact_kind` 仍为 `conflict-report`。它不是第九类工件，也不能被塞入审批、能力快照或执行证据。

### 3.2 拓扑顺序

规范依赖图为：

```text
rule assets + registry + structure + feature activation
                          |
                          v
composition proposal and conflict report
                          |
                          v
qa approvals bound to the composition report
                          |
                          v
final execution profile bound to report + approvals
```

该图必须可用稳定拓扑排序得到唯一阶段顺序。任何反向依赖、环、占位指纹、先生成最终 Profile 再补审批、事后重算旧审批指纹或试图寻找“固定点哈希”的流程均无效。

### 3.3 组合报告最低职责

`conflict-report` 2.2 至少规划以下封闭字段组：

- `candidate_groups`：覆盖全部规范组合键，而非只记录失败项；
- `scope_partitions`：记录原作用域、交集、差集、残余分区及守恒证据；
- `proposed_resolutions`：记录候选链、覆盖链、拟议最终值、最终来源和执行模式；
- `blocking_conflicts`：记录同层异值、交叉重叠、未知关系、低置信度自动化及其他阻塞；
- `diagnostics`：记录 preflight、越界、无效绑定和非候选诊断；
- `proposal_status`：至少区分 `blocked_conflict`、`awaiting_approval` 和 `resolvable`，但不得表示 delivery 或 `final_ready`。

组合报告只能包含稳定 ID、规范值、作用域、来源、指纹、状态和理由，不得包含正文、书稿对象载荷、私有规范原文或本地路径。

### 3.4 审批和最终 Profile

- `qa-approval-artifact` 2.1 绑定输入、结构图和组合报告，不绑定尚不存在的最终 Profile。
- 审批只处理报告中可审批的语义决定；它不能把 fatal diagnostic 或技术失败改写为通过。
- `final-execution-profile` 2.2 只在无 blocking conflict 且所需审批工件 schema、语义、指纹和绑定一致时构造。
- 无审批但存在需要审批的决议时返回 `awaiting_approval`，不得伪造审批或生成最终 Profile。
- P2b-C 不判断审批主体的权限充分性；完整 authority、阶段防旁路和审批状态机仍属于 P6。
- P2b 的所有结果固定为 disabled、`runtime_eligible=false`、`final_ready_eligible=false`、`delivery_allowed=false`。

## 5. 权威层级唯一真源

后续实现必须新增公开、版本化、只读、由 Schema 和 fixture 锁定的 authority contract。它是编译/验证资源，不是第九类运行工件，也不是用户可编辑的特性配置。

普通格式层的唯一顺序固定为：

```text
standard_supplement
< monograph_base
< book_type
< module
< publisher_template
< task_override
```

安全不变量独立于该顺序，并在候选收集前、合成后和执行前分别校验。任何普通层均不能覆盖安全不变量。

Composer 只能读取 authority contract；不得在 Python、Schema、测试或 fixture 中另建手工层级常量。Schema 的 `layer_kind` 枚举、validator 接受集合和测试向量必须由该合同生成或机械核对，差集不为零即失败。feature manifest 只能启用已存在能力，不能改变层数、顺序或权威含义。

## 6. 候选、覆盖链与置信度语义

### 6.1 候选链

- `candidate_chain` 保留全部 applicable 候选，按层级从低到高排列。
- 同层候选只按规范化 source identity 和 candidate identity 稳定排序；排序不增加权威。
- 被高层覆盖的低层候选仍为 applicable，继续留在候选链中。
- 同一层、同一规范作用域、同一属性存在不同规范值时必须形成 blocking conflict，禁止 last-write-wins。
- 同层同值多来源可以共同保留，但不得伪装为多次 override。

### 6.2 覆盖链和最终来源

- `override_chain` 对每个参与有效决议的层最多保存一个稳定代表，顺序从低到高。
- 同层同值多来源由规范身份选出该层代表；其余来源仍留在候选链和 provenance 中。
- `final_source` 从最终胜出层的同值候选中按规范身份选择稳定代表。
- 稳定代表选择只为了跨平台可重复表达，不提高来源权威，也不抹除其他来源。

### 6.3 置信度

置信度门禁固定如下，P2b-C 不得临场决定：

| 候选/拟议结果 | automatic 处理 | 非 automatic 处理 |
| --- | --- | --- |
| high | 仅在安全、能力、作用域、冲突和审批门禁均通过时可保持 automatic 候选资格 | 可进入 proposal/report/QA/保持路径 |
| medium | 不得直接形成 automatic 结果；必须有与该组合键及范围绑定的有效 QA 决议后，才可形成仍为 disabled 的拟议结果 | 可进入 proposal/report/QA；不得因同值 high 来源而隐藏 |
| low | 任何拟进入 automatic 的候选均为 blocking conflict；同值 high/medium 候选不能掩盖它 | 只允许 report、blocked_qa 或明确保持原稿的审批路径 |

最终 confidence 采用保守值：参与最终决议且仍 applicable 的候选中取最低置信度，不得只取 `final_source` 的置信度。

### 6.4 真正排除项

`excluded_candidates` 只允许以下稳定原因：

- `out_of_scope`
- `module_out_of_scope`
- `invalid_binding`
- `qa_exclusion`

新版 Schema 必须删除或禁止 `lower_precedence` exclusion。无效或越界的整个资产属于 preflight fatal diagnostic，不得通过将全部候选放入 excluded 来冒充已成功消费。

## 7. P2b-S 作用域代数

### 7.1 纯接口

P2b-S 必须提供无副作用、确定性的纯接口：

- `normalize_scope`
- `scope_equal`
- `scope_intersection`
- `scope_subset`
- `scope_difference`
- `scope_partition`
- `scope_disjoint`
- `scope_overlap_state`，结果仅为 `overlap`、`disjoint` 或 `unknown`

这些接口只处理规范作用域，不读取层级、不选择候选、不生成 Profile，也不修改运行入口。

### 7.2 关系处理

对同一 `semantic_object_kind + property_id`：

- equal：进入同一候选组，随后按权威层级决议；
- disjoint：可形成独立 resolved scopes；
- strict subset：高层只覆盖 subset，低层剩余区域必须显式分解为可证明且两两不相交的 residual scopes；
- crossing overlap：blocking conflict；
- unknown：blocking conflict；
- 含 `mutually_exclusive_conditions` 或 difference 无法确定性表达：blocking conflict；
- difference、intersection 或 partition 不能证明守恒：fail closed。

最终 Profile 中同一语义对象种类和属性的所有作用域必须 pairwise-disjoint。执行器只能消费已经分区的结果，不得重新计算 precedence、交集或差集。

### 7.3 分区不变量

每次 strict subset 分区必须同时证明：

1. 每个 residual 都是原低层作用域的子集；
2. residuals 两两不相交；
3. residuals 与高层作用域不相交；
4. `residuals ∪ higher_scope` 等于被分区的原有效区域；
5. 没有空分区、重复分区或不可寻址分区；
6. 输入排列、JSON 键序、Unicode 等价形式、操作系统和 Python 支持版本不改变结果。

测试必须包含生成式/性质测试和反例缩减，不能只依赖少数手工示例。

## 8. missing 与 module 边界

### 8.1 missing

P2b 不生成 `missing`。只有 P6 `prepare` 建立并批准完整目标对象全集后，才能证明某个预期对象/属性缺失。该调整只修订实现工作流，不改变 171 个 V040 决策的主责归属。

P2b 的报告可以写“未提供目标全集，未执行 missing 检测”，但不得把没有候选解释为缺失、合规或保持原状。

### 8.2 module 和无效资产

- 资产进入 composer 前必须通过 Schema、registry、binding、模块总体边界和 rule scope subset preflight。
- 无效绑定、module 越界、无法证明 subset 或资产级作用域矛盾形成 fatal diagnostic，资产不得进入 validated composition，且 `final_profile=None`。
- 只有合法资产内部的个别候选因对象作用域、批准排除或明确 module 子范围而不适用时，才进入组合报告的 excluded/diagnostic 记录。
- preflight 诊断与已验证候选的组合冲突必须分开计数和报告。

### 9.1 P2b-H：DAG、版本路由与 canonical hardening

**入口：** V0.4.1.1 方案已合并；以届时最新、明确锁定的 `main` 为基线。

**范围：**

- 新版工件 Schema 和无环 bindings；

- authority contract 唯一真源；
- canonical composition hardening；

- `$ref` 循环、越界、未解析、远程网络引用或 digest 不匹配均拒绝；

**严格门禁：** blocking conflict、fatal diagnostic、无所需审批、指纹失配或不稳定分区均返回 `final_profile=None`。审批充分性不在 C 中实现；C 只校验已声明的 Schema、语义、指纹和绑定一致性。任何产物仍为 non-delivery 且 runtime-ineligible。

**禁止、默认和回滚：** 不修改现有执行路径、DOCX、monograph-base、状态机或 CLI；feature 默认 false。回滚只删除 C composer、2.2 组合 fixture 和特性声明，不影响 H/S 的独立合同。

**不能宣称：** 未实现 P6 authority/防旁路、missing、DOCX 格式化、长文台账、Word 收敛、`final_ready`、delivery、能力启用、发布或公共 CLI。

## 12. 非目标与不能宣称的能力

本方案及后续三个 P2b 切片均不得据此宣称：

- 已建立或启用 monograph-base；
- 已实现 science-engineering-monograph 或其他领域模块；
- 已完成用户/出版社审批权限充分性状态机；
- 已处理 DOCX、真实书稿、长文对象台账、断点恢复或 Word 分页；
- 已实现 `missing`、通用 `allOf`、delivery 或 `final_ready`；
- 已启用、发布 V0.4.1 或提供稳定公共 CLI；
- SHA-256 指纹可以抵御恶意宿主或等同数字签名。

## 13. 残余风险

- 作用域差集可能遇到无法有限表达的条件空间；此时必须阻塞，不能近似扩大或缩小作用域。
- authority contract 解决顺序漂移，但不能验证来源材料本身是否真实或获得合法授权。
- P2b-C 只验证审批工件结构和绑定，仍需 P6 验证授权链、主体权限和阶段防旁路。
- 完整目标对象全集尚未建立，因此 P2 阶段不能证明缺失覆盖。
- 2.2 工件会增加 Schema 和 fixture 维护面；显式版本矩阵和机械一致性检查是强制门禁。
- 纯 JSON 确定性不等于 DOCX 执行正确；后续执行器、审计、Word 和视觉验收仍分别负责证明。
