# format-monograph V0.4.1.1：P2 契约修订附录

## 1. 定位、基线与适用范围

本附录从 `main@52010c4c53cdcfc578a5f3335c59a01304045468` 建立，版本号为 **0.4.1.1**。它是 V0.4.1 的 P2 契约修订附录，高于 V0.4.1，但不占用既定的 V0.4.2 书籍类型扩展版本。

V0.4.1 方案仍是不可变历史快照。凡本附录明确列出的冲突条款，后续 P2 和相关 P6 实现以本附录为规范性权威；未被本附录修订的 V0.4.0、V0.4.1 条款继续有效。

本方案只修订工件依赖、版本路由、权威层级、候选语义、作用域代数及 P2 实施切片，不实现 Schema、JSON fixture、Python、测试、Profile、Skill、DOCX、运行入口或 CLI，也不启用、发布任何能力。

以下治理事实保持不变：

- V0.4.0 已确认的全部格式值和安全不变量不变。
- 当前用户/任务明确要求与后续 QA 决定仍是可覆盖格式层的最高权威；安全不变量不可覆盖。
- V040 决策仍为 171 个唯一 ID，主责统计仍为 `150/20/1`，本附录不新增、删除或迁移这些决策的主责版本。
- 八类运行工件保持不变，不新增第九种 `artifact_kind`。
- V0.4.2 仍负责书籍类型和领域模块，V0.4.3/V0.4.4 的对象台账、恢复和长文验收边界不变。

## 3. 八类工件与无环生命周期

### 3.1 工件数量不变

八类独立工件继续为：

1. `layered-rule-asset`
2. `final-execution-profile`
3. `qa-approval-artifact`
4. `legacy-migration-manifest`
5. `feature-activation-manifest`
6. `capability-snapshot`
7. `conflict-report`
8. `execution-evidence-artifact`

`conflict-report` 的新版标题和职责固定为 **composition proposal and conflict report（组合提案与冲突报告）**，但 `artifact_kind` 仍为 `conflict-report`。它不是第九类工件，也不能被塞入审批、能力快照或执行证据。

### 3.2 拓扑顺序

规范依赖图为：

```text
rule assets + registry + structure + feature activation
                          |
                          v
composition proposal and conflict report
                          |
                          v
qa approvals bound to the composition report
                          |
                          v
final execution profile bound to report + approvals
```

该图必须可用稳定拓扑排序得到唯一阶段顺序。任何反向依赖、环、占位指纹、先生成最终 Profile 再补审批、事后重算旧审批指纹或试图寻找“固定点哈希”的流程均无效。

### 3.3 组合报告最低职责

`conflict-report` 2.2 至少规划以下封闭字段组：

- `candidate_groups`：覆盖全部规范组合键，而非只记录失败项；
- `scope_partitions`：记录原作用域、交集、差集、残余分区及守恒证据；
- `proposed_resolutions`：记录候选链、覆盖链、拟议最终值、最终来源和执行模式；
- `fatal_diagnostics`：记录无效 artifact、Schema、registry、指纹、binding、整体 module asset 或安全硬失败；
- `unresolvable_blockers`：记录 crossing overlap、unknown、互斥条件无法证明、difference 无法表达和分区守恒失败；
- `approval_required_conflicts`：只记录可由语义决定机械闭合的冲突或决议；
- `diagnostics`：记录不改变门禁结论的 preflight 测量、合法候选排除和其他非候选信息；
- `proposal_status`：至少区分 `fatal`、`unresolvable`、`awaiting_approval` 和 `resolvable`，但不得表示 delivery 或 `final_ready`。

`approval_required_conflicts` 仅限同层同 exact scope 异值选择、胜出层 medium/low 置信度结果是否采用、`keep_original` 和 `qa_exclusion` 等具有封闭允许决定集的项目。每项必须给出稳定 `conflict_id`、`proposed_resolution_id`、`normalized_scope`、完整候选集合、允许决定以及选择候选时可引用的 `candidate_id`。任何不能以这些字段机械验证和应用的事项不得降级为可审批冲突。

组合报告只能包含稳定 ID、规范值、作用域、来源、指纹、状态和理由，不得包含正文、书稿对象载荷、私有规范原文或本地路径。报告一经盖章即不可变；审批和最终 Profile 只能引用，不能回写、覆盖或伪造其 `proposal_status`。

### 3.4 审批和最终 Profile

- `qa-approval-artifact` 2.1 绑定输入、结构图、`composition_report_fingerprint`、`conflict_id`、`proposed_resolution_id` 和同一 `normalized_scope`；决定选择候选时还必须绑定该报告中的 `candidate_id`。它不绑定尚不存在的最终 Profile。
- 陈旧报告、扩域 scope、未知 conflict/resolution ID、非允许决定、候选不属于该冲突或任一指纹不匹配的审批均无效。
- `fatal_diagnostics` 不能由 QA 关闭，始终导致 `final_profile=None`。
- `unresolvable_blockers` 不能由 QA 把技术上不可表达的作用域改写成可执行结果；必须修正规则或作用域并重新组合，始终导致 `final_profile=None`。
- P2b-C 可以对 `approval_required_conflicts` 执行纯机械 resolution application，但不判断 actor authority。只有全部此类项目均有结构、语义、指纹和绑定一致的决定，机械应用后 unresolved approval-required 为 0，且 fatal/unresolvable 均为 0，才可构造 disabled 的 `final-execution-profile` 2.2。
- 无审批但存在需要审批的决议时返回 `awaiting_approval`，不得伪造审批或生成最终 Profile。
- 原 composition report 保持审批前事实；最终 Profile 以 `conflict_id + qa_decision_id` 记录闭合证据，不得把旧报告改写成 resolved。
- P2b-C 不判断审批主体的权限充分性；完整 authority、阶段防旁路和审批状态机仍属于 P6。
- P2b 的所有结果固定为 disabled、`runtime_eligible=false`、`final_ready_eligible=false`、`delivery_allowed=false`。

## 5. 权威层级唯一真源

后续实现必须新增公开、版本化、只读、由 Schema 和 fixture 锁定的 authority contract。它是编译/验证资源，不是第九类运行工件，也不是用户可编辑的特性配置。

普通格式层的唯一顺序固定为：

```text
standard_supplement
< monograph_base
< book_type
< module
< publisher_template
< task_override
```

安全不变量独立于该顺序，并在候选收集前、合成后和执行前分别校验。任何普通层均不能覆盖安全不变量。

Composer 只能读取 authority contract；不得在 Python、Schema、测试或 fixture 中另建手工层级常量。Schema 的 `layer_kind` 枚举、validator 接受集合和测试向量必须由该合同生成或机械核对，差集不为零即失败。feature manifest 只能启用已存在能力，不能改变层数、顺序或权威含义。

## 6. 候选、覆盖链与置信度语义

### 6.1 候选链

- `candidate_chain` 保留全部 applicable 候选，按层级从低到高排列。
- 同层候选只按规范化 source identity 和 candidate identity 稳定排序；排序不增加权威。
- 被高层覆盖的低层候选仍为 applicable，继续留在候选链中。
- 同一层、同一 exact 规范作用域、同一属性存在不同规范值时必须形成 `approval_required_conflict`；只有报告给出的封闭选择可以由有效决定机械闭合，禁止 last-write-wins。
- 同层同值多来源可以共同保留，但不得伪装为多次 override。

### 6.2 覆盖链和最终来源

- `override_chain` 对每个参与有效决议的层最多保存一个稳定代表，顺序从低到高。
- 同层同值多来源由规范身份选出该层代表；其余来源仍留在候选链和 provenance 中。
- `final_source` 从最终胜出层的同值候选中按规范身份选择稳定代表。
- 稳定代表选择只为了跨平台可重复表达，不提高来源权威，也不抹除其他来源。

### 6.3 置信度

置信度门禁在作用域分区和 authority precedence 完成后，针对每个最终原子 scope 的 winning layer/effective candidate group 计算，P2b-C 不得临场决定。被更高层覆盖的低层候选继续保留在 provenance 中，但不降低胜出结果置信度，也不触发该原子 scope 的审批；如果低层候选在 residual scope 仍为 winning，则只在该 residual 上应用门禁。

| winning group | automatic 处理 | 非 automatic 处理 |
| --- | --- | --- |
| high | 仅在安全、能力、作用域及其他门禁均通过时可保持 automatic 资格 | 可进入 proposal/report/保持路径 |
| medium | 固定为 `approval_required`；必须有与该组合键、原子 scope 和拟议结果绑定的有效决定，才可机械闭合为仍 disabled 的结果 | 可进入 proposal/report/QA，不得直接执行 |
| low | automatic 请求固定为 `approval_required` 或更强的安全/能力阻塞；只有明确采用该结果或 `keep_original` 的决定才可机械闭合，仍 disabled | 只允许 report、QA 或明确保持原稿路径 |

winning layer 内同一规范值的多来源组成 effective candidate group，其最终 confidence 取该组最低值，防止同层 low 被 high 隐藏。不同规范值仍按同层冲突处理，不能先混算置信度。该规则不跨层取最低值，也不允许低层弱来源反向阻塞更高层用户或出版社覆盖。

### 6.4 真正排除项

`excluded_candidates` 只允许以下稳定原因：

- `out_of_scope`
- `module_out_of_scope`
- `qa_exclusion`

Schema、registry 或 normalization 无效的 binding 属于 `fatal_diagnostic`，不得进入 validated `candidate_chain`，也不得成为普通 excluded candidate。新版 2.2 Schema 必须删除或禁止 `invalid_binding` 和 `lower_precedence` exclusion；已提交 2.0/2.1 enum 保持不变。整体 module 越界仍为 fatal，只有合法 module 内某候选对目标范围不适用时才可使用 `module_out_of_scope`。

## 7. P2b-S 作用域代数

### 7.1 纯接口

P2b-S 必须提供无副作用、确定性的纯接口：

- `normalize_scope`
- `scope_equal`
- `scope_intersection`
- `scope_subset`
- `scope_difference`
- `scope_partition`
- `scope_disjoint`
- `scope_overlap_state`，结果仅为 `overlap`、`disjoint` 或 `unknown`

这些接口只处理规范作用域，不读取层级、不理解“高层/低层”、不选择候选、不生成 Profile，也不修改运行入口。P2b-C 先按 authority contract 决定哪个作用域作为 `cut_scope`，再把通用 `source_scope/base_scope` 与 `cut_scope` 交给 P2b-S。

### 7.2 关系处理

对同一 `semantic_object_kind + property_id`：

- equal：两个 scope 表示同一规范区域；是否进入同一候选组由 P2b-C 决定；
- disjoint：可形成独立 resolved scopes；
- strict subset：从 `source_scope/base_scope` 中减去 `cut_scope`，剩余区域必须显式分解为可证明且两两不相交的 residual scopes；
- crossing overlap：返回不可安全分区证据，由 P2b-C 记录为 `unresolvable_blocker`；
- unknown：返回 unknown 证据，由 P2b-C 记录为 `unresolvable_blocker`；
- 含 `mutually_exclusive_conditions` 或 difference 无法确定性表达：返回不可表达证据，不接受 QA 改写；
- difference、intersection 或 partition 不能证明守恒：fail closed，并由 P2b-C 记录为 `unresolvable_blocker`。

最终 Profile 中同一语义对象种类和属性的所有作用域必须 pairwise-disjoint。执行器只能消费已经分区的结果，不得重新计算 precedence、交集或差集。

### 7.3 分区不变量

每次 strict subset 分区必须同时证明：

1. 每个 residual 都是原 `source_scope/base_scope` 的子集；
2. residuals 两两不相交；
3. residuals 与 `cut_scope` 不相交；
4. `residuals ∪ intersection(source_scope, cut_scope)` 等于被分区的原 `source_scope`；
5. 没有空分区、重复分区或不可寻址分区；
6. 输入排列、JSON 键序、Unicode 等价形式、操作系统和 Python 支持版本不改变结果。

测试必须包含生成式/性质测试和反例缩减，不能只依赖少数手工示例。

## 8. missing 与 module 边界

### 8.1 missing

P2b 不生成 `missing`。只有 P6 `prepare` 建立并批准完整目标对象全集后，才能证明某个预期对象/属性缺失。该调整只修订实现工作流，不改变 171 个 V040 决策的主责归属。

P2b 的报告可以写“未提供目标全集，未执行 missing 检测”，但不得把没有候选解释为缺失、合规或保持原状。

### 8.2 module 和无效资产

- 资产进入 composer 前必须通过 Schema、registry、binding、模块总体边界和 rule scope subset preflight。
- Schema、registry、normalization 或 fingerprint 无效，整体 module 越界，无法证明资产边界 subset，或资产级作用域矛盾形成 `fatal_diagnostic`，资产不得进入 validated composition，且 `final_profile=None`。
- 只有合法资产内部的个别候选因对象作用域、批准排除或明确 module 子范围而不适用时，才进入组合报告的 excluded/diagnostic 记录。
- preflight 诊断与已验证候选的组合冲突必须分开计数和报告。

## 9. 三个实际实现切片

三段实现必须严格串行：P2b-H 合并并满足退出门禁后，才从新的 `main` 建立 P2b-S；P2b-S 合并并满足退出门禁后，才建立 P2b-C。每段均使用独立 Draft PR、独立双重审查和用户明确合并授权。

### 9.1 P2b-H：DAG、版本路由与 canonical hardening

**入口：** V0.4.1.1 方案已合并；以届时最新、明确锁定的 `main` 为基线。

**范围：**

- 新版工件 Schema 和无环 bindings；
- 显式 artifact/registry/authority 版本路由；
- authority contract 唯一真源；
- canonical composition hardening；
- 唯一拥有 `feature-activation-manifest` 2.1 Schema、`profile_v2_composer` 字段声明、默认 `false`、对 `profile_v2_schema` 的依赖及版本路由测试；
- 不实现 scope algebra 或 composer。

**算法不变量：**

- `oneOf` 每个分支必须有真实正例、反例及新增分支证据；
- `allOf` 只允许按 Schema path + node digest 锁定的现有 QA 条件 guard；任何新增、未知或结构型 `allOf` 在生产 canonical 路径 fail closed；
- 不宣称通用 `allOf` 支持；
- `x-semantic-fingerprint=exclude` 沿完整 `$ref` 链单调继承，任一层 exclude 即 exclude，不提供“取消排除”覆盖；
- `$ref` 循环、越界、未解析、远程网络引用或 digest 不匹配均拒绝；
- 生产 canonical path 和证据 inventory 使用同一 composition policy。

**合同与测试：**

| --- | --- | --- |
| V0411-H-DAG-001 | 无环工件绑定与拓扑顺序 | T411-H-DAG-001..012 |
| V0411-H-ROUTE-002 | 显式版本/registry 兼容矩阵 | T411-H-ROUTE-001..018 |
| V0411-H-AUTHORITY-003 | authority contract 单一真源 | T411-H-AUTH-001..012 |

## 13. 残余风险

- 作用域差集可能遇到无法有限表达的条件空间；此时必须阻塞，不能近似扩大或缩小作用域。
- authority contract 解决顺序漂移，但不能验证来源材料本身是否真实或获得合法授权。
- P2b-C 只验证审批工件结构和绑定，仍需 P6 验证授权链、主体权限和阶段防旁路。
- 完整目标对象全集尚未建立，因此 P2 阶段不能证明缺失覆盖。
- 2.2 工件会增加 Schema 和 fixture 维护面；显式版本矩阵和机械一致性检查是强制门禁。
- 纯 JSON 确定性不等于 DOCX 执行正确；后续执行器、审计、Word 和视觉验收仍分别负责证明。
