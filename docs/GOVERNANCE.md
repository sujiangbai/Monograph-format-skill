# 仓库治理规则

## 1. 权威分支

`main` 是唯一稳定分支。空仓库首次初始化治理与 V0.1 方案是唯一允许直接写入 `main` 的例外。

## 2. 分支与 PR

首次基线之后，任何修改必须先创建分支：

- `plan/vX.Y.Z-topic`：方案修订。
- `skill/topic`：核心 skill 与脚本。
- `adapter/topic`：平台安装或兼容适配。
- `fix/topic`：缺陷修复。

每个分支必须创建 PR。PR 应说明变更、原因、用户影响、验证结果和未决风险。默认采用 squash merge。

## 3. QA 合并闸门

PR 完成验证后必须向仓库所有者提供 QA 摘要。只有收到明确的合并授权后才能合并；测试通过不等于自动授权。

## 4. 当前方案与历史快照

- 用户已确认的当前方案入口为 [`plans/monograph-mvp-development-plan.md`](plans/monograph-mvp-development-plan.md)，随本 PR 合入 main 后生效；用户明确要求高于历史条款。
- 当前方案在固定文件中修订，通过分支、PR、Git 历史和简短修订记录追溯；不再强制每次创建更高版本文件或并行附录。
- 已提交的 `docs/plans/vX.Y.Z-*.md` 保留为不可变历史快照，不修改、不删除，不作为独立实施权威。
- 方案和实现的当前入口由 `docs/plans/INDEX.md` 明确。方案合并后，依赖实现从最新 main 开始；已有可复用实现保留。
- 目标、内容修改权限、格式范围或验收标准改变时先取得用户确认；已授权范围内的实施细节和局部修复无需重复批准。方案确认和上传不等于合并或发布授权，第 3 节继续适用。

## 5. 核心与适配隔离

`format-monograph/` 只包含开放 Agent Skills 核心，不引用 Agent 私有工具或绝对路径。平台差异只能进入 `adapters/`，且不得改变内容保护、规则优先级和验收标准。

## 6. 数据与版权

禁止提交：

- 用户书稿、格式修改成品和渲染页面。
- 未获公开授权的出版社规范、模板、样书或截图。
- 含个人信息、密钥或访问令牌的文件。

可以提交经用户确认可公开的规则摘要，以及完全合成、不含真实出版内容的测试数据。

## 7. 发布质量

任何格式修改交付必须保留原稿，验证正文内容一致性，并逐页渲染检查。不能渲染时必须明确降级，不得宣称通过视觉验收。
